# Frontend Conventions

For UI work, read [DESIGN.md](DESIGN.md) first. For endpoint additions/changes, read the [API contract](../backend/AGENTS.md#api-contract). These documents own visual behavior and wire rules respectively.

## Architecture

Feature-Sliced Design is checked by Steiger. Dependencies point downward: app → _pages → widgets → features → entities → shared. Import other slices through their index; use relative imports within a slice. Entities do not import each other; compose them in pages. Server-only exports use `index.server.ts`, separate from the client barrel.

- `app/`: thin Next route shells exporting a page; a staff route shell may wrap it in `PermissionGate` (see the admin shell below). The public root is the exception: it redirects by session and app host before rendering `StoreSitePage`. `(admin)` owns theme wiring; `(public)` has none. Crossing root layouts reloads the page.
- `_app/`: initialization/providers; `_pages/`: scope-prefixed page slices; `widgets/`: composite UI; `features/`: user actions; `entities/`: domain data/types/API; `shared/`: infrastructure and primitives.
- There is no route guard: no Next proxy and no shell redirects by user type (ADR 0035). An unauthenticated visit reaches the shell, and the session restore in `shared/api/client.ts` sends it to `/auth/login?next=<path>`, carrying the fragment as the login URL's own fragment (fragments never reach the server). A session hitting another area gets the backend's 403; inside the staff shell, a page the caller lacks the permission for is sent to the landing (see the admin shell below). A page that renders without calling an API does not redirect until its first request. Public Server Components resolve the store per request from the Host via `resolveHost()` (`shared/api/index.server`) and pass it down as props; the app domain reaches client components through `useAppDomain()`, provided by both root layouts. Cross-cutting invariant tests live in `src/__tests__/`.
- `@/*` resolves to `src/*`; TypeScript and Jest must agree.

## Fetching and store context

Use `shared/lib/hooks` for fetch lifecycles. Pick `useListPage` for every paged list (pager: `ListPage` on a list screen, `Pager` from `@/shared/ui` inside a panel or dialog), `useManagedList` for a whole list, and `useResource` for one value, optional fetching, dependency-driven reload, replacement after writes, or a 404 split. For a plain unparameterized array, either of the last two fits. Failure/loading presentation and retry semantics are defined in [DESIGN.md](DESIGN.md#通知と失敗状態). A file download is an entity function over `fetchBlob` (`shared/api`: expected media types, fallback message, the server's JSON error read out of the Blob) driven by `useBlobDownload` (`shared/lib/hooks`: abort, object URL lifetime, saving, retry); its failure renders as a `RegionError` in the region that offered the download.

Writes whose response can be lost belong to one of two backend families (ADR 0037). Receipt-module operations (GLOSSARY「操作の受領」; advertising costs, remuneration, reviews, surveys) look up the receipt before any business validation and never physically delete their target, so a business rejection of an unchanged replay proves the first attempt did not land; `useOperation` relies on exactly that rule. Row-key operations keep the key on the target row and keep their own ordering: point adjustments, attribution corrections, applicant attachments and scheduled-task runs may validate before the key lookup (ADR 0037 gives point adjustments as the example), so they stay off the hook. Notification drafts are row-keyed too, but they look up the dedupe key before any business validation and have no delete path, so the rule holds for them. Receipt-module operations and notification drafts go through `useOperation` (`shared/lib/hooks`). It mints the key once, keeps the operation per (operation name, user id, the store the page shows — the URL store id), refuses to send when the user changed, replays only the stored content and key, and owns the one rule for when a result-unknown operation may be forgotten; pages render its `pending` and never classify statuses for that purpose themselves. Pick `memoryOperationStore` unless the operation must survive a reload, and never put amounts or free text in `sessionOperationStore` without that need. The entity write function takes the key and the axios config as separate arguments; the hook passes the operation's store as `X-Store-ID`.

A write that carries the shown object's `version` goes through `useVersionedWrite(reload)` (`shared/lib/hooks`; `useDeleteAction` is built on it). It sends one write at a time, toasts the outcome, applies the success response through `onSuccess`, reloads on 404, and on 409 raises `conflict` and refuses further writes until its `reload()` runs; route every reload of that object through `reload()`. A 409 here means the shown object may be stale, so the answer is always to reload; it is also returned for business conflicts (duplicate name, already stopped) and cannot be told apart, which is safe for the same reason. This is not `useOperation`, whose 409 is a settled receipt mismatch that is never reloaded. Pages only choose the presentation from the returned outcome: a banner that keeps unsaved input (detail editors), or an immediate `reload()` (list rows and dialogs, which keep the dialog open on 409). Do not branch on `isConflict` / `isNotFound` for such a write.

There is one admin shell (`widgets/admin-shell`), mounted once by `app/(admin)/(staff)/layout.tsx`, the common parent of `admin/` and `store/` (so crossing between them does not remount it or refetch stores/me/menus; `admin-shell-mount.test.ts` pins this); the cast/member portals sit outside `(staff)` with their own layouts, both built on `PortalShell` (`widgets/portal-shell`; see DESIGN.md「本人ポータル」); `/admin/**` and `/store/**` are mount prefixes without authorization meaning; `/auth/**` holds the public login / registration / invitation / LINE callback / initial-setup pages. The admin shell mounts three seams:

- `StoreContextProvider` / `useStoreContext`: the URL decides the context. Store pages live at `/store/{storeId}/**` (route `store/[storeId]/`); `currentStoreId` is the URL store id read by `storeIdOf(pathname)` (`shared/lib/store-route`), and the api client injects `X-Store-ID` from the same reading on every request sent from a store page (API paths carry no prefix to tell store-level endpoints apart; handlers that do not take the current store ignore the header). There is no current-store cookie or state, so tabs never affect each other. The provider fetches the caller's authorized stores (`GET /stores/me`, newest-created first) once; the shell renders `/store/**` children only when the URL store is in that list (otherwise, including for an empty set, it fetches nothing and leaves for the landing with a warning toast), keyed by the store id so moving to another store remounts the page. Store page components read the URL store id from the context: `useCurrentStoreId()` where they need it as a non-optional string (path building), `useStoreContext().currentStoreId` otherwise. `/admin` pages inject nothing; the one exception is a cross-store list reading a single row's store-level data (order correction history from `/admin/orders`, offered only to callers holding the store-tree `ORDER_MANAGE`), which passes the row's store as an explicit `X-Store-ID`. Do not fetch the same list per consumer.
- `MenuProvider` / `useMenuTrees` (`entities/menu`): `GET /menus/me` once per shell; it returns one tree per context (`GROUP` / `STORE`), each only when the caller holds a permission of that tree (a failure reads as no tree). The sidebar's context rail is a list of links derived from it: the group (when the group tree is returned) to `/admin/dashboard`, and every authorized store (when the store tree is returned) to `/store/{id}/dashboard`. The selected entry and the panel follow the URL only (`/admin/**` → group, `/store/{id}/**` → that store); the panel shows that tree's dashboard and section headings (items are split by tree, never by path prefix; store-tree paths are relative to the store and get `/store/{id}` prepended; a caller with no tree, or a store-only caller on an `/admin` page, gets only the group dashboard link). The rail is hidden when there is only one context. `/admin` is the landing page: `useLandingPath()` (`widgets/admin-shell`) resolves the first rail entry — the group dashboard when the group tree is returned, else the newest-created store's dashboard — and the page replaces itself with it. A staff page the caller may not open leaves the same way (ADR 0042): `PermissionGate codes={[...]}` (all required) wraps the route shell, or the page judges its own permission and renders `DeniedPage`; both go through `LeaveToLanding`, which replaces the URL with the landing and raises one `notify.warning`, but shows the denial in place when the denied page is the landing itself. `staff-route-permission.test.ts` fails for a staff route that does neither and is not listed as open. A 403 after the page opened (permission revoked mid-session) stays the page's own failure display.
- `MeProvider` / `useMe`: the caller's `user_type`, `permissions`, `email`, `display_name` from `GET /me`, held for the layout's lifetime (never persisted); update through `setMe` so all consumers observe the response without a refetch. Gate UI with `hasPermission(me, code)`; while `me` is null (loading or failed) show nothing permission-gated, and page-level gates render `MePending`. The frontend never decodes the JWT (`no-jwt-decode.test.ts`). `MeProvider` is mounted by the admin shell and by `MemberPortalLayout` (which reads `email_verified` for the unverified-email banner on every member page); the cast portal has none, so widgets also mounted in the cast portal take capabilities as props instead of calling `useMe()`. Tests mock `useMe` at `@/entities/user/model/MeContext`, not the barrel, because `MePending` imports it relatively.

Staff management (`_pages/admin-staff`) is a list at `/admin/staff` plus create / edit screens at `/admin/staff/create` and `/admin/staff/[id]/edit`, covering every staff member; account actions (suspend, resume, password reset) stay on the list rows. Service identities (`_pages/admin-service-identities`) follow the same shape at `/admin/service-identities`, `/create` and `/[id]/edit`. Both create / edit screens share `GrantForm` (`features/staff-management`), whose store choices come from the context's own authorized stores (a staff grant must be a subset of the grantor's).

Server-side code (Server Components) reaches the backend through `backendUrl()` in `shared/lib/backend-url`: `BACKEND_URL` carries the host only, and the endpoint path stays in code. Every compose file sets it to the gateway's internal entry point (`http://gateway:8081`) so server-side calls get the gateway's per-replica health checks and retry; the code default `http://backend:8080` only serves runs outside compose. Do not reintroduce env vars that carry an endpoint path — a pinned value in an existing `.env` silently outlives every path rename.

Session tokens (ADR 0036): the access token and its user id live only in `shared/api/session.ts` (tab memory); nothing writes them to a cookie or Web Storage (`no-jwt-decode.test.ts`). Continued login rides on the backend's HttpOnly `refresh_token` cookie. `SessionGate` (`_app`, mounted by `app/(admin)/layout.tsx`, the common root of the staff shell and the cast/member portals) calls `restoreSession()` once per document before rendering, so each shell's `GET /me` carries the token. A 401 runs one shared refresh and re-sends the request once; a second 401, or a refresh 401 other than `credential_changed`, goes to login. `credential_changed` and the refresh's 409 (the refresh cookie belongs to another account) only raise a dialog and wait for the user; never navigate or reload automatically. The refresh never refetches `/me` (permission changes bump the credential version and fail it instead). A re-sent request keeps its original `X-Store-ID`, and an explicitly given `X-Store-ID` is never overwritten by the URL store. While the `credential_changed` prompt is up, later 401s neither refresh nor navigate; its button carries `next` like the 401 path. The login page tries `requestRefresh()` once and lands without showing the form on success, except that a non-member session whose `next` is a `/member/` path gets the form (the member portal sent it after a 403), so the member can log in. Logout calls `/auth/logout` first (the backend reads the Bearer for the session), then `endSession('logout')`; other tabs leave only when their memory user id matches. Every session start and end goes through `shared/api/session.ts`: `landSession(kind, refreshExpiresAt, next)` starts the `session-kind` cookie and returns `next` when it is a same-site relative path for that kind (`shared/lib/navigation`: member `/member/`, staff `/admin/` and `/store/`, cast `/cast/`; no `//`, scheme, `\` or `.`), else the default landing; `extendSession` renews the cookie after a refresh; `endSession(reason)` looks up what to clear in one table (the token always; cookies and the `sessionOperationStore` pending operations only for logout / unsupported / relogin; the broadcast only for logout). The return path lives only in the URL: `redirectToLogin({ returnHere: true })` builds it from the current location, the login and register pages forward it to each other (`ReturnCarryingLink`), and the LINE login stores it with `state`. Navigation stays with the caller. Nothing else calls `startSession` / `clearSession` from `shared/lib/session.ts`. Requests whose 401 the caller handles itself (login, refresh, logout, credentialed invitation acceptance) set `skipAuthRedirect`. Pending operations are keyed by the memory user id, not email.

Store paths are assembled only in `shared/lib/store-route` (`storePath(storeId, subPath)`). `store-path-invariants.test.ts` catches raw interpolated store paths but not every concatenation; review remains necessary. Login lands staff on `/admin` (the landing page above); the `session-kind` cookie holds the session kind `admin` / `cast` / `member`, expires with the refresh token, and is the only cookie the public root reads to redirect.

## Public templates and shared UI

- Public pages load `_pages/store-site/templates/<key>/<page>.tsx` through `loadTemplatePage`; unknown keys use the default template's same page. Preserve that dynamic import contract. Pages are page / casts / cast-detail / schedule / menu / about / reservation / reviews / news / news-detail.
- Shared sections live in `templates/_sections/`, never as a template key. Template directories contain themes and layouts. `entities/store-profile/getTemplateMeta` owns text-slot metadata used by site and settings.
- Import shadcn primitives through `@/shared/ui`, except the chart: import it from `@/shared/ui/chart`, because a barrel re-export puts the whole recharts library into the chunk every page loads. For any shared/ui change, consult DESIGN.md's vendored/authored classification; generated primitives stay frozen.
- Toast call sites use `@/shared/notify`. Direct Base UI toast imports are limited to that module and `shared/ui/toast.tsx`; this also applies to dynamic imports and test mocks not caught by ESLint.
- Dialogs outside `shared/ui` draw their frame with `DialogFrame`; ESLint rejects importing `DialogContent` there (including `import * as` from `@/shared/ui`). The AlertDialog family (`ConfirmDialog`) is separate and unrestricted.

## Code and checks

- Components/types use PascalCase; internal variables/functions follow TypeScript conventions. API **property names** remain snake_case. Store-facing identifiers use Store; the unified account is User.
- PermissionCode in `entities/user/model/types.ts` mirrors the backend enum manually; update both when adding a permission. There is no parity test.
- A disabled Steiger rule needs a Japanese reason in `steiger.config.mjs` (the mandatory-comment exception). Keep `_pages` excessive-slicing suppression scoped to pages.
- Docker lint runs format:check, lint, lint:fsd, typecheck. Run all four for local verification. Coverage and final Taskfile/PR checks are documented in [CONTRIBUTING.md](../CONTRIBUTING.md).
