# Infrastructure Conventions

- **Environment directories**: `infrastructure/development/` (HTTP only) and `infrastructure/release/` (HTTPS, Let's Encrypt, web→websecure redirect). Each holds its own `docker-compose.yml`, `Taskfile.yml`, and `traefik/`. Copy `infrastructure/.env.example` into each environment directory as `.env`. Switch with `task up env=release` (default is development).
- **In a git worktree, `task up` (development only) copies `.env` from the main checkout** when the worktree has none (`ensure-env` in `development/Taskfile.yml`). It never overwrites an existing file, and `release/` has no such fallback — it simply fails without `.env`.
- **`infrastructure/docker-compose.example.yml`** is the baseline compose template (same service structure as the per-environment files): apply structural service changes there first, then mirror them into `development/` and `release/`.
- **Traefik routing**: traefik uses only the file provider — routes live in each environment's `traefik/dynamic.yml` (e2e: `e2e/traefik/dynamic.yml`), never in container labels, and no compose file mounts `/var/run/docker.sock` (do not reintroduce the docker provider: the socket is host root). To expose a single-instance service, add a router, a service addressed by compose service name (`http://storage:8333`), and any middleware there. Paths are dispatched by `PathPrefix` (backend = `/api`, static = `/static`, frontend = everything else). If an app is unaware of its prefix, add a `stripPrefix` middleware (e.g. `backend-strip`). The file provider gets no compose interpolation; `release/traefik/dynamic.yml` reads the TLS domain through traefik's `{{ env "APP_DOMAIN" }}` template, so the gateway must receive `APP_DOMAIN` in its `environment`. A malformed `dynamic.yml` leaves traefik with zero routers while its `--ping` healthcheck stays healthy.
- **Replicas**: `backend` / `frontend` run `deploy.replicas: ${BACKEND_REPLICAS:-1}` / `${FRONTEND_REPLICAS:-1}` and carry no `container_name` (compose names them `<project>-<service>-<n>`, resolvable on the compose network). Each `dynamic.yml` (e2e included) renders their `servers` with a Go-template `range` over the same variables plus `COMPOSE_PROJECT_NAME`, which the gateway therefore receives in its `environment` — the replica count has one source, and changing it needs the gateway recreated too (`up -d` does this, since its environment changes). Each replica is health-checked individually (backend `/actuator/health/readiness`, frontend `/health`) and a `retry` middleware resends connection failures (idempotent requests only) to another replica. Do not collapse the upstream back to `http://backend:8080`: Docker's DNS round-robin gives neither per-replica health checks nor even spread over keep-alive connections. Compose has no rolling update: `up -d` after an image change recreates all replicas at once.
- **Runtime sizing**: each replica gets `deploy.resources.limits.memory` (`BACKEND_MEMORY_LIMIT` / `FRONTEND_MEMORY_LIMIT`). The backend heap is a percentage of that limit, set by `JAVA_TOOL_OPTIONS` in `backend/Dockerfile` (with G1 explicit, since below ~2 GiB the JVM would pick SerialGC); Node sizes its V8 heap from the limit on its own. Operator JVM flags go through `JDK_JAVA_OPTIONS`, which the launcher reads after `JAVA_TOOL_OPTIONS` — never set `JAVA_TOOL_OPTIONS` in compose or `.env`: it replaces the image default wholesale, and a value-less compose entry is passed as an unset that silently drops it. The backend healthcheck is itself a `java` process in the same container and inherits both variables, so operator flags that bind a port or load an agent break it — there is no way to unset an env var for a Docker healthcheck in a shell-less image. CPU is deliberately not limited. `PORT` / `HOSTNAME` / `NODE_ENV` of the frontend are image constants (the gateway and healthcheck hard-code port 3000).
- **Backend configuration**: the backend reads Spring Boot's own environment variable names (relaxed binding: `spring.datasource.hikari.maximum-pool-size` ← `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE`, `app.jwt.secret` ← `APP_JWT_SECRET`); `application.yml` holds literal defaults only, with no `${CUSTOM_NAME:default}` placeholders. The backend service takes the whole environment directory `.env` through `env_file`, and its `environment` lists only (a) values shared with another container under that image's name, mapped onto the Spring name (`SPRING_DATASOURCE_PASSWORD=${POSTGRES_PASSWORD…}`, `SPRING_DATA_REDIS_PASSWORD=${REDIS_PASSWORD…}`, `APP_UPLOAD_*_KEY=${S3_*…}`, `APP_PRIVATE_ATTACHMENTS_*_KEY=${PRIVATE_S3_*…}`), (b) connection targets fixed to compose services, and (c) release's `:?` guards for required secrets. `environment` beats `env_file`, so those cannot be redirected from `.env`. Do not add a pass-through list or invent a new name for a Spring property. A key declared empty in `.env` reaches the backend as an empty string and overrides the default, which is why `.env.example` keeps optional keys commented out. `log4j2.xml` reads `LOG_DIR` / `LOG_LEVEL` / `APP_LOG_LEVEL` straight from the environment, outside Spring.
- **DB / Redis**: referenced by the service names `database` / `cache`. Migrations are Liquibase (`backend/src/main/resources/db/changelog/`).
- **Network and host aliases**: in `development/` (and the example template) the `gateway` service carries the aliases `store1.kizuna.test` / `kizuna.test`; `release/` has none, since it is reached through real DNS. The frontend (`resolveHost()` in `frontend/src/shared/api/host.ts`) tells store sites from the app host by Host, and callers inside the compose network resolve those names through these aliases. Development must also set `APP_DOMAIN=kizuna.test` in its `.env` — the example file ships `kizuna.jp`, and `resolveHost()` treats only `APP_DOMAIN` as the app host, so with the example value the aliased `kizuna.test` root resolves as a _store_ instead of the app host (admin console). Renaming an alias is the silent failure — it degrades into a DNS failure inside whatever is calling.
- **E2E does not use this stack.** `e2e/docker-compose.e2e.yml` stands up its own disposable copy (same services, tmpfs data, no host ports, project name derived from the worktree) so that e2e and the development stack — and e2e runs from worktrees with distinct basenames — do not collide. Each gateway resolves `backend` / `frontend` / `storage` through its own compose network's DNS, so the stacks cannot claim each other's routes.
- **Secrets**: `.env` must not be committed.

## Services (compose project `kizuna`)

Eight services in development: `database`, `cache`, `backend`, `storage` (SeaweedFS, serves `/static`), `private-storage` (separate SeaweedFS for applicant attachments, ADR 0033), `mailpit`, `frontend`, `gateway`; release has no `mailpit`. Images and ports live in the compose files — read them there rather than trusting a copy here. Four things the compose files do not make obvious:

- **Service name ≠ container name** for `cache` (container `redis`) and `gateway` (container `traefik`), and `backend` / `frontend` have no fixed container name at all (replicas are `kizuna-backend-1`, `kizuna-backend-2`, …): from the repository root, `task -d infrastructure/development logs service=cache` takes the service name, raw `docker` commands take the container name. Address `backend` / `frontend` through `docker compose -p kizuna <command> backend` (works from any cwd, covers every replica) rather than a container name.
- **Storage access**: S3 is exposed through `/static` on the gateway. Development and the example template enable the Admin UI at `http://localhost:23646`, bound to host loopback only. Release and E2E keep the Admin UI disabled with no storage host ports. WebDAV is disabled in all environments.
- **Private storage**: `private-storage` has no Traefik route, no host port and no Admin UI in any environment, and its volume is deliberately not backed up — never add a route, port or backup for it. Its credentials (`PRIVATE_S3_*`) must differ from the public `S3_*` ones, or the backend refuses to start. Operations (rotation, enablement checks) are in `infrastructure/README.md`.
- **Mail catcher**: development and E2E point the backend's environment-based SMTP (`SPRING_MAIL_HOST` / `SPRING_MAIL_PORT`, the fallback used while the DB system config `smtp_host` is blank) at `mailpit:1025`, hard-wired so `.env` cannot redirect it; development also pins `SPRING_MAIL_USERNAME` / `SPRING_MAIL_PASSWORD` empty and SMTP auth / STARTTLS off, because `env_file` would otherwise deliver release's SMTP credentials from a `.env` copied from the example. Development exposes the Web UI at `http://localhost:8025` (host loopback only); E2E publishes no port and steps read it through `MAILPIT_URL`. Release has no `mailpit` and reads `SPRING_MAIL_*` from `.env` — never add the service there.
