# Backend (Java) Conventions

## Module structure (Spring Modulith)

Each module under `com.kizuna` follows the DDD four layers — `domain/` / `application/` (use-case services = the transaction boundary) / `infrastructure/` / `api/` (controllers, `dto/` + MapStruct mappers, and the mount directories `me/` / `auth/` for the controllers under the `/me/**` and `/auth/**` prefixes; a module without them is normal, not incomplete); `shared/` is the OPEN shared kernel.

### Layer / module rules

- **Aggregate = JPA entity** (rich model): no public setters on the fields an aggregate declares. Already applied in the rich-model modules cast / customer / order / member / shift / user. Modules not yet enriched (store / menu / settings / storeprofile) will adopt this incrementally; **do not add new public setters in new code** (the base-class setters inherited from `BaseEntity` — id / timestamps — and `StoreScopedEntity` are a known exception, slated for gradual removal). Construction uses `@Builder` (consumed by MapStruct); partial updates use a domain-owned `XxxPatch` record + `apply()`; state transitions are behavior methods (e.g. `Order.complete()/cancel()`, with invalid transitions raising a domain exception → 400).
- **Cross-aggregate references are by ID only** (`Order.customerId`, etc.). DB foreign keys are kept. Object assembly happens in the application layer; lists and details use projections (e.g. `OrderView` + JPQL join — reference entity names by FQCN to avoid HQL reserved-word collisions).
- **Synchronous references between modules** go only through packages exposed via `@NamedInterface` (document transitional exceptions in package-info.java). Events use `@ApplicationModuleListener` + the event publication registry (`event_publication` table, spring-modulith-starter-jdbc).
- **Application services are concrete classes by default** (FooService = class). An interface + Impl split is introduced only when a second adapter actually exists, or when a consumer in another module mocks it (current cases: SystemConfigService, FileStorageService). A second legitimate interface is the **inbound port that breaks a module cycle**: the consuming module declares it in its own `application/` package and the providing module implements it (`MemberRankMetrics` in member, implemented by order's `AttributionMaterializer`; `SpecialServiceRejectionHandler` in service, implemented by order's `OrderSpecialServices`). Do not introduce single-implementation interfaces for any other reason.
- **Paths carry no authorization meaning.** The only URL prefixes are `/me/**` (`api/me`, self-service derived from the principal) and `/auth/**` (`api/auth`); every other controller sits directly in `api/` with an unprefixed path, and whether a handler needs a store is stated by `@CurrentStore`, not by its path. Authorization has exactly two axes: permissions (`@PreAuthorize` on `PERM_*` authorities) and the caller's store set ∩ current store. The store set is resolved per request from the DB (`StoreScopeResolver` → `StoreScopeHolder`, installed by `StoreScopeInstallingInterceptor` on every path), never carried in the JWT. There is no group/store "side", no console qualification, and no emergency elevation.
- **The current store is a handler argument**: a handler that needs it declares `@CurrentStore Long storeId`, and `CurrentStoreArgumentResolver` validates `X-Store-ID` in this order — absent, non-numeric or out of long range → 400; an authenticated caller holding no `PERM_*` authority, or naming a store outside its resolved set → 403; a store that does not exist → 400 (checked after the set, so a SPECIFIC_STORES caller cannot tell a missing store from a forbidden one). Anonymous callers may name any store (the public site). `@CurrentStore(required = false)` resolves an absent header to `null`; a handler that does not declare it ignores the header. Maintenance mode returns 503 only for handlers declaring a required `@CurrentStore`, before the header is validated.
- **Store isolation is stated in every query**: store-scoped entities extend `StoreScopedEntity` and their repositories extend `StoreScopedRepository` (no `findById` / `findAll` without a store condition; a `Specification` puts `storeId` on its root). Handlers receive the current store as `@CurrentStore Long storeId`, services take it as their first parameter, and every query carries `storeId` on the root and on each joined or sub-queried store-scoped entity. Reads across a store set take the caller's `StoreScope` as a parameter: SPECIFIC_STORES → `store_id in (:storeIds)`, ALL_STORES → no store condition (two query methods, or the condition appended only for SPECIFIC_STORES; never `(:param is null or …)`). Creation sets `storeId` explicitly (from the parameter, or copied from the parent row); `StoreScopeStampListener` only rejects a null `storeId`. An intentionally cross-store query is keyed by its real boundary (token digest, user id, member id) and states that boundary in one line on the repository declaration. Nothing behind the query enforces the store: correctness rests on review and e2e.

## Code Conventions

- **Naming**: classes, methods, and variables are CamelCase. DB columns (snake_case) are mapped by JPA; API JSON keys (snake_case) are mapped by Jackson.
- **Store-side vocabulary uses the Store prefix**: StoreVO, StoreProfile
- **Adding a `PermissionCode`** is more than the enum: bump the literal count assertion in `PermissionCodeTest`, add the code to the hand-maintained union in `frontend/src/entities/user/model/types.ts` (no parity test exists), add the catalogue row and the default-role grant rows to the baseline `seed/01-roles.yaml` (pre-launch the baseline is edited in place; `PermissionSeedLiteralTests` pins seed ≡ enum), and record the grant in `DefaultGrantApprovalTests`. `reconcile/` only inserts missing catalogue rows and seeds grants when it creates a default-role row for the first time — it never rewrites grants on an existing DB, because administrators may edit default roles.
- **Imports**: no inline FQCN usage, no wildcard imports (`*`); one explicit import per class.
- **Constructor injection**: dependencies come in via the constructor. A pure field-assignment constructor must be replaced by Lombok `@RequiredArgsConstructor`; hand-writing a constructor is allowed only when it performs real construction logic beyond assignment (e.g. building a configured `TransactionTemplate`).
- **Formatting**: Spotless + Google Java Format on JDK 25. The version and daemon JVM are pinned in the build configuration; use the Taskfile for final verification.
- **Coverage**: the only Jacoco exclusions are `**/api/dto/**` (DTOs + MapStruct-generated code), `**/shared/config/**` (pure configuration), and `**/Application.class`. **The domain layer must always be covered.**
- **DB migrations**: read [database rules](src/main/resources/db/AGENTS.md) before touching changelogs. The pre-launch baseline is edited in place; that document owns checksum handling, seed rules, FK constraints, and dev-DB recreation. Never remove database volumes.
- **Authentication**: Spring Security AuthenticationManager, NimbusJwtDecoder and NimbusJwtEncoder (HS256). APP_JWT_SECRET has no default and must be at least 32 bytes (startup validation). Revocation uses token-specific logout and account credential-version equality. DB is authoritative, Redis caches monotonically, and revocation cache changes must follow transaction commit. Re-enabling an account must not revive old sessions.
- **Config values**: read from `AppProperties` (shared/config). No hardcoding.
- **Logging**: keep the `[req=<id>-store=<id>]` MDC prefix from `log4j2.xml` (hyphen, no space).
- **Modulith docs**: `ModularityTests` generates local documentation under `backend/docs/modulith/`; generated output is not committed.
- **Optional filter queries**: the JPQL `(:param is null or ...)` pattern can cause a runtime 500 due to PostgreSQL parameter type inference (see `CustomerService.searchSpec`). Build variable filter conditions with a `Specification` instead.
- **Manual API verification**: when hitting an endpoint that declares `@CurrentStore` directly with curl, send `X-Store-ID: <id>`; without it the request is 400. `X-Role` is ignored.

## API contract

This section is the normative source for all HTTP endpoint additions and changes. Before implementing a task spanning frontend and backend, present the paths/methods, success and principal failure codes, request/response fields (types and optionality), authorization, and pagination for approval. Prefer safety, then consistency with the established contract, then textbook REST style. Document code deviations separately; do not copy them or mix unrelated endpoint repairs into the change.

### Resources and responses

- Use plural kebab-case nouns; a genuinely singleton child may be singular. Domain actions use noun subresources (`POST /orders/{id}/completion`), not bare verbs. Irreversible transitions need their own authorization, reason, and explicit rejection of a repeated transition. Do not replace domain operations with generic CRUD.
- Literal path segments may coexist with `{id}`, but reserve those values permanently. `/me/...` owns reads and writes derivable from the authenticated principal (profile, password, self-service data).
- `GET` is side-effect-free; `POST` creates resources or performs actions; `PUT` replaces one resource at its own URI, never at a collection root; `PATCH` partially updates; `DELETE` deletes.
- A read accepting a secret token uses `POST` with a body, such as invitation `/view`. Never move the token to a path or query, where logs/history/Referer can expose it. Wire anonymous CSRF handling at the same time.
- Creation returns **201** with the resource id; no `Location` header is required. Deletion returns **204** without a body. Actions return **200** with a result, **201** if creating a resource, or **204** when the consumer only removes/refetches data.
- Authentication failure is **401**, permission denial **403**, invalid input/transition **400**, absent or scope-invisible resource **404**, and conflicts **409** through the existing exception mapping. Do not independently change a family's denial semantics to hide enumeration.
- `CommonExceptionHandler` owns `{ "error": "…", "details": { "field_name": "…" } }`; `details` is optional. Messages must be authored user-facing copy. Never forward framework/DB exception text, SQL, constraint names, or stack traces. Unhandled errors use a fixed 500 message. Use the established `ServiceException`, `ConflictException`, and `NotFoundException` families where applicable. Bearer authentication failures are handled by `JwtAuthenticationEntryPoint`; login failures also use the exception handler.
- JSON field names and validation detail paths are snake_case. User-defined Map keys are data and must not be renamed by that strategy.
- New body DTOs use `XxxRequest` / `XxxResponse`. Lists use separate Summary DTOs; details carry the heavier fields. Secret values and unnecessary sensitive PII must be absent from the list DTO **type**, not hidden by mapper ignores, nulls, or serialization rules.

### Pagination

- Use Spring `Page` for a numbered list with a total count. Sort by a total order ending in a unique key.
- Use `CursorPage` for queues, infinite scrolling, and growing history without counts. Apply `MAX_SIZE`; the cursor comparison must use the same ordered column tuple, including its unique tie-breaker.
- A bare `List` is only for a small, explainably bounded collection. Growing history is not bounded. State the bound when introducing a list endpoint.

### Authorization and anonymous endpoints

`SecurityConfig` uses `anyRequest().permitAll()`: method annotations are the authorization boundary. Every handler must be **public, non-final, non-static**, with `@PreAuthorize` or `@PermitAll`; proxy-ineligible methods silently bypass method security. `EndpointAuthorizationDeclarationTests` enforces this without exemptions. Permission authorities must resolve to `PermissionCode` (`PermissionLiteralTests`).

For each anonymous endpoint, check all four concerns:

1. Declare `@PermitAll` on the handler.
2. For anonymous writes, add the **actual method plus path** to `SecurityConfig.CSRF_IGNORED_MATCHERS`. A path-only matcher also exempts authenticated sibling methods. Bearer-header requests already have their own CSRF exemption.
3. If stale Bearer credentials must be ignored, add the **method plus path** to `ExemptingBearerTokenResolver.BEARER_EXEMPT_MATCHERS`. Do not exempt optional-authentication handlers that inspect `Principal`: doing so discards valid credentials too. Test anonymous access with a broken Bearer, not just without credentials.
4. A handler serving one store's public data declares `@CurrentStore`: anonymous callers may name any existing store through `X-Store-ID`, so it must expose only that store's public data. A handler that reads no store does not declare it and ignores the header.

One capability has one endpoint. A read of one store's data declares `@CurrentStore` and takes the store from `X-Store-ID`; do not add a twin that takes `store_id` as a query. When a cross-store reader (e.g. `ORDER_SET_VIEW`) also needs that read, widen that handler's condition to the union of the permission families instead. Only reads without a current store (cross-store lists and aggregates) take the caller's `StoreScope` from `StoreScopeHolder` (null → 403) and pass it down. Such a read that would share its method and path with the single-store read of the same resource takes the literal segment `cross-store` under that resource (`GET /orders/cross-store`, `GET /operational-reports/cross-store`). Store reads carry the store condition in the query itself (see the store isolation rule above). A path that must read across stores is keyed by its real ownership boundary, and a test pins that boundary.

### Existing deviations

Do not replicate or opportunistically rename `/staff`, `StoreVO` / `StoreStatusVO` / `MenuVO`, `Token`, or `StoreCreateDTO` / `StoreUpdateDTO`. Existing path-only anonymous matchers do not relax the method-plus-path rule; their repair requires checking sibling methods and optional authentication together.
