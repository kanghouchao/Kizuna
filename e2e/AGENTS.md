# E2E Conventions (playwright-bdd)

Human-facing docs (how to run, the Japanese Gherkin keyword table, local iteration without Docker) live in [`README.md`](./README.md) — read it for anything not covered here.

- **Structure**: `features/**/*.feature` (scenarios) + `steps/**/*.ts` (step definitions) + `base-url.ts` (the single source of `BASE_URL` / `APP_URL`) + `playwright.config.ts` (two `defineBddProject` projects: `initial-setup` and `chromium`) + `docker-compose.e2e.yml` (a **self-contained disposable stack** — DB / Redis / SeaweedFS / backend / frontend / gateway plus the runner).
- **The e2e stack shares nothing with the development stack**: no host ports, no `container_name`, tmpfs data, and both the compose project name and the image tags are derived from the worktree name (`task e2e` exports `COMPOSE_PROJECT_NAME` / `E2E_IMAGE_TAG`). Distinct worktree basenames let two worktrees run e2e at the same time (equal basenames share the derived names) — do not reintroduce a fixed project name, a fixed image tag, or a published port. The gateway routes through `e2e/traefik/dynamic.yml` (file provider, upstreams by compose service name), so it only reaches its own stack's containers.
- **The seeds ship no stores and no accounts; the `initial-setup` project creates them first.** It registers `admin@kizuna.test` through the initial-setup page, then creates stores `store1.kizuna.test` / `store2.kizuna.test` through the store API (left `PREPARING` — nothing in the suite gates on store status) and `tanaka.hanako@kizuna.test` / `yamada.jiro@kizuna.test` through the staff API (password `pass1234` for all three). The main `chromium` project waits for it via `dependencies` and does not run when it fails. Keep `features/initial-setup/` out of the main project's `features` glob, keep `retries: 0` on the setup project (a retry after a successful registration fails because staff already exists), and keep its `steps` limited to `steps/initial-setup.steps.ts` — other steps files carry untagged `After` hooks that log in as the 店長 before it exists. Since the main project loads that file too, it must not gain untagged hooks or step texts that collide with existing ones.
- **The suite runs serially against one shared live store** (`fullyParallel: false`, `workers: 1`). That is what makes module-scoped step state and snapshot/restore hooks safe — raising the worker count breaks both.
- **Scenarios are Japanese Gherkin**: every `.feature` starts with `# language: ja` and uses `機能` / `シナリオ` / `前提` / `もし` / `ならば`. **Step definitions stay on the English `createBdd()` API** (`Given` / `When` / `Then`) and match the Japanese scenario lines by regex or cucumber expression.
- **Requests that any second steps file could want belong in `steps/store-api.ts`** — login (`loginAsStoreAdmin`, `loginViaUiAndEnterStore`), the store-context header (`X-Store-ID`), and cast (incl. invitations, field definitions) / shift (incl. request approval) / customer / member (registration, link) / order (cancel, application decline) / store-config helpers are already there. A one-off lookup used only by a single teardown may stay local (as in `cast-custom-fields.steps.ts`), but it must still build its headers from `STORE_HEADERS` rather than restating them.
- **A restore hook that writes back a captured snapshot must be sentinel-guarded**: record whether the snapshot step actually succeeded, and skip the restore when it did not — a scenario that fails _before_ the snapshot would otherwise PUT an empty object and wipe live data (the `custom_texts` case in `steps/store-settings.steps.ts`). Guard the write itself, not the login before it. A hook that restores a _fixed known value_ instead (`template-switch.steps.ts` → `template_key: 'default'`) needs no sentinel and should stay unguarded: silently swallowing that failure would leave the shared dev store poisoned for every later run.
- **Address data by ids read at runtime, not by fixed ids**: `store-api.ts` deliberately pins the store-context ids and the 店長 login, both created by the `initial-setup` project (`STORE1_ID`, `ADMIN_EMAIL`) — that is the one place for them (the setup project registers `store1.kizuna.test` first on the empty DB and asserts at runtime that it got id `STORE1_ID`). Elsewhere take the store id from `loginViaUiAndEnterStore` (the UI auto-selects the first authorized store, which is store 1 for the 店長 created by `initial-setup`; the helper returns `STORE1_ID`) rather than restating the id. This rule is about ids, **not** credentials: the UI login step takes the address and password of an `initial-setup` account as inline Gherkin parameters across the suite, which is what keeps each scenario explicit about _who_ is logging in.
- **Run from the repo root**: `task e2e`, which needs `jq` on the host (see README for what it does and where artifacts land). `task e2e grep=<regex>` narrows the main `chromium` project only and `shard=i/n` splits it; both reach `playwright.config.ts` as `E2E_GREP` / `E2E_SHARD` env vars. Keep `grep` on the main project — a config-level `grep` also filters out `initial-setup`, and the subset then runs with no accounts.
- **Static types**: `task lint service=e2e` checks all authored TypeScript through Docker without a browser or database; default `task lint` and CI Repo Lint include it. The E2E runner checks types before generating and running scenarios.
- **Full-stack E2E runs in CI** (`.github/workflows/e2e.yml`): one image build, four shards each on its own disposable stack, then one `E2E` check that merges the blob reports. Before opening a PR, run locally only the scenarios the change touches (`task e2e grep=...`); the full suite is CI's job. Sharding changes which features precede which on the shared store, so an assertion that depends on rows left by earlier features is a bug in the assertion — fix it there, never by pinning file order.
