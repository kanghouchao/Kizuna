# E2E Conventions (playwright-bdd)

Human-facing docs (how to run, the Japanese Gherkin keyword table, local iteration without Docker) live in [`README.md`](./README.md) — read it for anything not covered here.

- **Structure**: `features/**/*.feature` (scenarios) + `steps/**/*.ts` (step definitions) + `base-url.ts` (the single source of `BASE_URL` / `PLATFORM_URL`) + `playwright.config.ts` (`defineBddConfig`) + `docker-compose.e2e.yml` (a **self-contained disposable stack** — DB / Redis / MinIO / backend / frontend / gateway plus the runner).
- **The e2e stack shares nothing with the development stack**: no host ports, no `container_name`, tmpfs data, and both the compose project name and the image tags are derived from the worktree name (`task e2e` exports `COMPOSE_PROJECT_NAME` / `E2E_IMAGE_TAG`). That is what lets two worktrees run e2e at the same time — do not reintroduce a fixed project name, a fixed image tag, or a published port. The gateway's traefik is constrained to its own compose project (`--providers.docker.constraints`); without it every traefik on the daemon claims every other stack's containers, since the router names are identical across stacks.
- **The suite runs serially against one shared live store** (`fullyParallel: false`, `workers: 1`). That is what makes module-scoped step state and snapshot/restore hooks safe — raising the worker count breaks both.
- **Scenarios are Japanese Gherkin**: every `.feature` starts with `# language: ja` and uses `機能` / `シナリオ` / `前提` / `もし` / `ならば`. **Step definitions stay on the English `createBdd()` API** (`Given` / `When` / `Then`) and match the Japanese scenario lines by regex or cucumber expression.
- **Requests that any second steps file could want belong in `steps/store-api.ts`** — login (`loginAsStoreAdmin`, `loginViaUiAndEnterStore`), the store-context headers (`X-Role` / `X-Store-ID`), and cast (incl. invitations, field definitions) / shift (incl. request approval) / customer / member (registration, link) / order (cancel, application decline) / store-config helpers are already there. A one-off lookup used only by a single teardown may stay local (as in `cast-custom-fields.steps.ts`), but it must still build its headers from `STORE_HEADERS` rather than restating them.
- **A restore hook that writes back a captured snapshot must be sentinel-guarded**: record whether the snapshot step actually succeeded, and skip the restore when it did not — a scenario that fails *before* the snapshot would otherwise PUT an empty object and wipe live data (the `custom_texts` case in `steps/store-settings.steps.ts`). Guard the write itself, not the login before it. A hook that restores a *fixed known value* instead (`template-switch.steps.ts` → `template_key: 'default'`) needs no sentinel and should stay unguarded: silently swallowing that failure would leave the shared dev store poisoned for every later run.
- **Address data by ids read at runtime, not by seed ids**: `store-api.ts` deliberately pins the store-context ids and the seeded login (`STORE1_ID`, `ADMIN_EMAIL`) — that is the one place for them. Elsewhere read `storeId` from the landing URL (`loginViaUiAndEnterStore` returns it) rather than restating a seed id. This rule is about ids, **not** credentials: the UI login step takes the seeded address and password as inline Gherkin parameters across the suite, which is what keeps each scenario explicit about *who* is logging in.
- **Run from the repo root**: `task e2e`, which needs `jq` on the host (see README for what it does and where artifacts land).
- **E2E does not run in CI** — running it before opening a PR is the author's responsibility.
