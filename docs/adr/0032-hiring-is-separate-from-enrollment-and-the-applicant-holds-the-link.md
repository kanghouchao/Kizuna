# 採用の確定と在籍の作成を分け、応募者が在籍への参照を持つ

Status: Accepted（裁定は #396、2026-10-29）

## 決定時の背景

応募者（Applicant）は選考中の本人の実データ（連絡先・経歴・面接内容）を持つ正本で、キャスト在籍（CastEnrollment）と公開プロフィール（CastProfile）は顧客に見せる展示側の正本である（ADR 0026）。採用が決まった応募者を在籍へ引き継ぐとき、二つの正本をどう結ぶかに三つの選択肢があった — 採否確定と同時に在籍を作る、在籍が応募者を指す、応募者が在籍を指す。

## 決定

- **採用（HIRED）の確定と在籍登録は別の操作**とする。HIRED は RECRUITMENT_DECIDE による選考の終端で、在籍は作らない。採用済み応募者に対する明示的な在籍登録（RECRUITMENT_VIEW + CAST_MANAGE）が `CastService.create` を呼び、在籍と未公開プロフィールを作る。
- **応募者が在籍 ID を持ち、在籍は応募者を知らない。** `t_applicants.enrollment_id` は可空で、部分唯一索引により一つの在籍は最大一つの応募者からしか指されない。同じ応募者への再登録は 409。
- **入店日（started_on）は在籍の属性**とする。直接作成の経路でも必須（既定は当日）で、既存行は created_at の日付で埋める。応募者は入店日を持たず、在籍を経由して読む。

## 理由

- 在籍作成には源氏名や公開項目が要り、面接の場で確定する採否とは入力の時点が違う。同時に作ると採否確定が展示情報の入力に縛られ、在籍作成の失敗が採否の記録まで巻き戻す。
- 在籍は応募者を経ずにも生まれる（直接登録・再入店・招待先行）。在籍側に `applicant_id` を置くとほとんど空の列になり、作成経路ごとに埋める判断が要る。加えて recruitment は在籍登録で cast に依存するので、cast が recruitment を参照すると依存が環になる。GLOSSARY の「応募者を在籍の前段状態として持たない」はこの方向を指す。
- 入店日は在籍区間の事実で、再入店は新しい在籍行として自分の入店日を持つ。応募者に置くと再入店の日付の置き場が無く、採用効果（媒体別の入店・定着）の分母が揃わない。

## 帰結

- 在籍詳細から来歴の応募者を見せたい場合は `enrollment_id` の逆引きで行い、在籍側に列を足さない。
- 応募者の匿名化（保持方針）は在籍に触れない。参照の向きがそれを保証する。
- 採用効果の集計は応募者の媒体名と在籍の入店日・終了日だけで算出でき、状態履歴を再計算しない。
