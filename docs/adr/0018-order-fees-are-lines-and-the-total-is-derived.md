# 受注金額は明細行で持ち、合計は行から導出し、写しへは回写しない

Status: Accepted

## 決定時の背景

手入力の total_fee と固定列・jsonb の内訳が別々に更新され、合計の一致と適用コース名を保証できなかった。名称の写しと金額を持つ明細行から合計を導けば、将来マスタが導入されても過去の受注を書き換えずに済む（#380 / #384 / #747）。

## 決定

- **受注金額の内訳は受注明細（`t_order_fee_lines`）として持つ**。1 行＝種別（enum）＋名称の写し＋帯符号の
  金額で、外部から行を名指して変更しない。
- **種別は八枚の閉集合**: `BASE_COURSE` / `EXTENSION` / `OPTION` / `SURCHARGE` / `DISCOUNT` /
  `MANUAL_ADJUST` / `POINT_REDEMPTION` / `CREDIT_SURCHARGE`。指名・受付区分・場所エリア等の加算は
  `SURCHARGE` へ集約し、区別は名称の写しが担う。**ホテル代・交通費・釣銭は受注金額外の回収・精算項目**で
  あり、種別を持たないことで型の側から排除される（横断形式は #386 の領分）。
- **符号は種別が決める**。保存する金額は帯符号で、加算の種別は 0 以上、減算の種別（割引・ポイント利用）は
  0 以下、手動調整だけが両方を取る。行レベルの DB CHECK（`ck_t_order_fee_lines_amount_sign`）が同じ
  規則を持ち、閉集合の外の種別も塞ぐ。**表示層（DTO・UI）は減項を正値へ翻して見せる** — 引くことは種別が
  表すので、入力にも符号を書かせない。
- **`total_fee` は導出列**。手入力の口を廃し、行を動かす集約の行為メソッドが毎回総和を書き直す。列を残すのは
  一覧・集計が行を畳まずに読めるようにするためで、正本は行の側にある。**合計を機械和から外したい場面は
  手動調整の行で表す**。`completeWith` の合計引数は退場した。
- **行は負を取れるが、総和は負にならない**。`total_fee` はどの時点でも 0 以上を不変量とし、負になる
  差し替え・完了は「内訳の総和が負になっています。割引・調整の金額を見直してください」で撥ねる（集約が
  総和を書き直す場所で検証し、`t_orders.total_fee` の DB CHECK を二重の守りに置く。訂正の門は同じ
  不変量を固有の文言で既に守っている）。過剰割引・返戻は受注金額の内側に表現を持たない — 回収・精算
  （#386）の領分である。
- **通常編集・完了・訂正は取得時の版を名指す**。`expected_version` が現物と異なれば 409 を返す。
- **作成・申請確定・編集・完了・訂正は試算後に明示確認する**。保存時に同じ入力を再計算し、
  操作者・店舗・対象・入力・計算結果を結ぶ `confirmation_token` と照合する。採用条件・会員資格・
  利用単位・付与結果が変われば再確認を要求し、残高だけの変動で利用可能なら同じ結果として扱う。
- **ポイント利用の行はシステム専有**。完了処理が台帳の減算仕訳と対で書く唯一の経路で、店舗の明細差し替えは
  この種別を作れず、既にある行も消せない。完了後訂正でもこの行を編集しない（ADR 0019）。利用の打消しは台帳の明示操作（ADR 0023）が担う。
- **一受注に一つのコーススナップショットを持つ**。設定・歴史版本の ID、版本番号、名称、時間、価格、
  固定報酬、採用根拠、採用日時を保存する。作成・申請確定では現在条件を採用し、通常編集では
  `course_id` の指定時だけ再採用する。他の明細はコース変更に連動して再採用しない。
- **基本コース料金は快照から一行生成する**。名称・金額の手入力を受け付けない。固定報酬は割引・
  ポイント利用で減額しない。設定変更・論理削除は既存受注と訂正前快照へ遡及しない。

## 帰結

- 「内訳の和＝合計」は構造で成立する。集約経由では和≠合計の状態を作れず、集約を迂回する書き込み（一括更新・
  native UPDATE）は適応度テスト（`OrderFeeLineAggregationTests`）と統合テスト（`OrderFeeLineIT`）が
  検出する。跨表のため宣言的な DB 制約では書けず、trigger は導入しない。
- **`total_fee` はポイント利用を引いた後の額になる** — 内訳の単純総和である以上、減算の行も含む。旧義の
  「会計金額」ではなくポイント控除後の請求額を指すので、この列を読む表示は名前を合わせる（アーカイブの行は
  「請求」と名乗る）。付与の基準と利用の上限は、ポイント利用の行が入る前の総和で決める（利用するほど付与も
  減る、という挙動を避けるため）。
- 総和の不変量が入る前は、完了前の編集が負の総和を保存できていた（総和への検査が無く、列にも CHECK が
  無い）。現在は baseline の CHECK と集約の検証で拒否する。適用済み開発 DB は DB 規約に従って再作成する。
- 負の総和での完了はこれまで利用ポイントの上限判定（`usePoints > chargeAmount`）が偶然拒んでいた —
  利用ポイントは常に 0 以上なので、負数との比較が常に真になるため。不変量が上限判定より先に正しい文言で
  撥ねる形になり、この偶然と無関係な文言への依存は消える。
- 既存の散列は明細へ吸収された: `manual_discount` → `MANUAL_ADJUST` 行 / `discount_name` → `DISCOUNT`
  行の名称 / `option_codes` → `OPTION` 行（1 件 1 行）/ `used_points` → `POINT_REDEMPTION` 行。読み口の
  利用ポイントはその行からの導出になる。`auto_grant_points` は残る（付与は内訳ではない）。
- 完了は採用済みコースを保持し、コース変更は先に通常編集で行う。完了後は歴史版本を選ぶ訂正だけが担う。
- 基本コース料金の行は集約が快照の名称・金額へ更新する。他の編集可能行は集合として差し替え、
  ポイント利用行は保持する。利用取消は ADR 0023 の台帳操作で扱う。
- コース以外の六種の明細は店舗入力を維持する。給与集計・保証・実支払の仕組みはこの適用の射程外である。
