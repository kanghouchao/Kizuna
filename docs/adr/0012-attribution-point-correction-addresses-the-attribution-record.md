# 誤帰属の台帳訂正は帰属記録を宛先に取り、無効化とは別段の人手操作とする

Status: Accepted

## Context

ADR 0009 は帰属記録の**無効化**を定め、台帳へは自動波及させず訂正は手動調整で行うとした。ところが
店舗コンソールにある唯一の調整口 `/store/customers/{customerId}/point-adjustments` は
`CustomerPointService#adjust` → `activeMemberId(customerId)` で**その顧客に現在紐づく会員**を解決する。
誤って付与された先は**帰属記録が持つ会員**（`t_order_attributions.member_id`、`updatable = false` の
不変値）であり、両者が食い違う経路が 3 つある。

1. **伝票トークンの申領で成立した帰属**（根拠 `RECEIPT_TOKEN`）: 申領は店舗台帳に顧客行も関連も作らない
   （ADR 0008）。顧客未設定の受注には顧客 ID そのものが無く、調整口へ到達する術がない。
2. **帰属のあと関連が解除された**: `activeMemberId` が null になり「会員に紐づいていない顧客のポイントは
   調整できません」で撥ねられる。
3. **帰属のあと関連が別会員へ張り替えられた**: 調整が**新しく紐づいた無関係な会員から引かれ**、誤って
   付与された側は手つかずで残る。3 つの中で最も危険で、誤りの上に誤りを重ねる。

ADR 0009 が別途裁定へ回したのは「既に費消されていて**引き切れない**」場合である。上記はそれ以前の
**宛先に到達できない／別人に当たる**という別の論点であり、同 ADR は想定していない。

一次資料の調査で、この領域には二つの規範があることが確認できた。ひとつは、追記型台帳の訂正は「元の行を
失効させる」のではなく「補償行を追記し、元の対象を**指し返す**」形であること — Fowler の Reversal
Adjustment、TigerBeetle の correcting transfer、Stripe、Salesforce、Shopify が一致し、反例が見つからない。
Stripe は層ごとに態度を変えており、授与（credit grant）は `voided_at` を持つ失効ができる一方、台帳
（customer balance transactions）は追記のみで「反対取引を作る以外に取り消す方法はない」。もうひとつは、
補償の引き落としが**元のロットを狙わず期限の早いロットから引く** fungible な減算であること
（Voucherify と Shopify が独立に一致）。後者は本システムにとって決定的で、既存の消費行が持つ引き当ては
**一切動かさずに済む**。

## Decision

- **宛先は帰属記録が持つ会員とし、受注を入口に辿る**。店舗コンソールの操作とし、受注 → 帰属記録 →
  `member_id` の順に辿る。店舗の境界を決めるのは受注だけで、これは無効化・再発行と同じ紀律である
  （帰属記録も台帳も platform 帰属で店舗行分離機構に載らない）。
- **訂正できるのは `INVALIDATED` の帰属記録に対してのみ**。有効な帰属は制度上まだ正しい付与であり、
  それを動かせることは「記録を訂正せずに会員の残高へ手を伸ばす」通路になる。順序は無効化が先、台帳が後。
- **要求は帰属記録を ID で名指し**、その記録が当該受注のものであることと `INVALIDATED` であることを
  検証する。**受注の現況では判じない** — 無効化のあと正しい本人が申領を済ませていれば受注には有効な
  帰属記録が並んで存在するが、古い無効化記録は依然として正当な訂正の根拠である。名指しを要求するのは
  並行操作で別の記録へ書くことを防ぐためでもある。
- **記帳は既存の手動調整（`MANUAL_ADJUST`）で、金額は人が決める**。減算は期限の早いロットから引く
  fungible な引き当てであり、誤って付与されたロットを狙い撃ちにはしない。狙い撃ちにしないからこそ、
  そのロットへ既に引き当て済みの消費行に手を触れずに済み、「引き当ての合計は減算量に一致する」という
  台帳の不変条件が最初から最後まで破れない。
- **残高が足りなければ全額を撥ねる**（部分的な引き当てを作らない既存の挙動のまま）。例外の文言が
  現在残高を載せているので、操作者は引ける額へ入れ直せる。**引き切れなかった差額の扱いは本 ADR でも
  定めない** — ADR 0009 が運用の実例へ委ねた裁定はそのまま生きている。
- **訂正の仕訳は `corrected_attribution_id` で帰属記録を指し返す**。FK は `ON DELETE SET NULL` —
  `CASCADE` は店舗削除が台帳行を道連れにして ADR 0006 に反し、`RESTRICT` は帰属記録が店舗削除を
  塞いでしまう。この列が非 null であること自体が「これは帰属の訂正である」を表すので、新しい仕訳種別は
  設けない。
- **同一の帰属記録に対する訂正の累計は、その受注がその会員へ与えた付与の合計を超えられない**。この口の
  授権は「その付与が誤りだった」ことだけに由来し、それを超えた分は通常の調整として顧客経路が扱うべき
  ものである。残高不足で全額を引けなかった後に会員が他店で貯めた分から引き継ぐ経路が正当である以上、
  上限が無ければ際限なく引ける。
- **累計の判定は、同じ冪等キーを持つ既存行を除いて数える**。除かないと、応答を取り逃した正当な再送が
  上限超過で撥ねられる — ADR 0007 が「再送の判定を入力検証より先に置く」ことで既に一度回避した罠と
  同型である。
- **無効化の権限を `POINT_ADJUST` と同格（店長限定）へ揃える**。無効化が `ORDER_MANAGE` だったのは
  端点が `OrderController` に載っている副作用であり、裁定の結果ではない。不可逆で準金銭的な操作の
  前段だけを店員に許すことは、`POINT_ADJUST` を店長限定にしている理由と矛盾する。両段が同一人物に
  揃うことで、やり残しの防止は画面の導線だけで足りるようになる。
- **語彙は「訂正」と「手動調整」に統一し、「清算」を退役させる**。同音の「精算」が本システムでは金流域の
  別概念（精算範囲・移動担当精算・店舗間精算）として現に生きており、読み上げでも文脈でも衝突する。
  加えて清算は債権債務を結び終える語で、与えられるべきでなかったポイントを引く操作の意味に合わない。
  ADR 0009 が既に持つ「訂正」の傘を台帳層まで広げ、機構名は既存の「手動調整」をそのまま使う。
- **訂正は order モジュールの独立したサービスが担い、`OrderAttributionService` は台帳を知らないまま
  据え置く**。あの依存の不在は ADR 0009 の「無効化は台帳へ自動波及しない」がコードに残した唯一の
  構造的な証跡であり、注釈だけがそれを主張する状態にはしない。

## Consequences

- ADR 0006 の運用上の前提（会員コード直指定の全会員照会口を店舗側に作らない）は保たれる。店舗が
  到達できる会員は「自店舗の受注に、名指しされた無効化済み帰属記録が存在する会員」に限られ、境界が
  「自店舗の顧客に ACTIVE な紐づけ」から同じ強さの別の事実へ移っただけである。二例目を作る際は
  同じ判定を経ること。
- **引き切れない差額の扱いは未裁定のまま**である。本 ADR は宛先へ到達する手段を与えるだけで、費消済みの
  ポイントを取り返す政策（再発行の保留・損失の受容・現金での求償）は定めない。一次資料でもここは
  三派に割れており（硬く撥ねる Shopify / Open Loyalty、既定で撥ねる Square、負残高を許す Salesforce、
  現金で求償する ANA）、写せる既定が存在しない。
- 店舗が削除されると受注が消え、帰属記録も CASCADE で消え、訂正仕訳の指し返しは null になる。
  訂正済みかの判定もそこで失われるが、判定の対象そのものが存在しなくなるため齟齬は生じない。台帳行は
  グループ資産として残り続ける（ADR 0006）。
- 店員は誤帰属を見つけても自分では訂正を始められなくなる。現場の即応性は下がるが、会員の残高を動かす
  操作は店長のものという既存の紀律と揃う。
- 訂正の仕訳が積み上がると明細が読みにくくなる。Fowler も同じ点を訂正の代償として挙げており、
  会員向けの明細読み口には対を畳んで見せる手当てが要る。
