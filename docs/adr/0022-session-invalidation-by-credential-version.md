# セッション失効は資格情報の版の照合で判定する

Status: Accepted

## 決定時の背景

#789（PR #797）はパスワード再設定のセッション失効を時刻境界で実装した — Redis の `blacklist:password-reset:{email}` に再設定時刻を置き、iat がそれより前のトークンを拒否する。codex 評で見送った 3 件の指摘は、根治手段が全て資格情報の版（credential version）に収束する: ①稼働中に `APP_JWT_EXPIRATION_MS` を短縮すると失効エントリが既発行の長寿命トークンより先に満了して旧トークンが復活し得る（停止用 `blacklist:users:` も同じ前提）、②iat が epoch 秒のため再設定と同一秒に発行済みだった旧トークンが最長 1 秒弱生き残る、③旧パスワードの照合後・発行前に再設定の commit が挟まると発行後 iat のトークンが正当として生き残る。三つとも「時刻を解釈して失効を判定する」ことに由来し、窓を個別に塞いでも同族が再生する。

決定前の機構には非対称も残っていた。代理再設定はアカウントの全セッションを失効させるが、自助変更（`PUT /platform/me/password`）は当該トークン 1 枚しか失効させず他端末は生き残る。停止→再開は `blacklist:users:` キーの削除で停止前のトークンが復活する。

## 決定

- **`t_users` に資格情報の版 `credential_version`（単調増分の整数）を持つ。** 楽観ロックの `version`（BaseEntity — 無関係な更新でも増える）とは別列。発行時にトークンの claim へ搭載し、検証時に現在の版と**相等比較**する。不一致も claim 欠落も拒否（fail-closed）。未上線のため移行期は設けず、配備時点の既発行トークンは全て失効する。
- **発火点はパスワード再設定（代理）・自助変更・停止の三つ。** 再開は失効機構に何もしない — 停止前のセッションは復活しない。ロール変更は発火しない（授権変更は次回ログイン反映、の既定方針を維持する）。
- **照合先は DB が正本、Redis は read-through キャッシュ。** キャッシュは TTL = JWT 有効期間、miss は DB の標量投影で照会して回填する。版の増分は commit 後にキャッシュへ**単調書き込み**（現在値 >= 新値なら書かない — 既存の `MONOTONIC_MARK` と同型の Lua）で反映し、回填も同じ単調書き込みを使う。DEL 方式は採らない: 増分前に DB から読んだ旧版が DEL の後に回填される競合で、旧版が TTL まで居座る。単調書き込みなら書き込みの到着順に依らず最大の版へ収束する。Redis 断連は現行どおり fail-closed。
- **版の増分は失われてはならない。** 実体の更新（楽観ロックが兜底）か原子 SQL（`credential_version = credential_version + 1`）で行う。読んだ値に +1 して書き戻す形や HQL 批量 UPDATE は禁止 — 並行する二つの発火が一回分に合流し、間に発行されたトークンが生き残る。
- **Redis 鍵の置換**: `blacklist:password-reset:` と `blacklist:users:` は機構ごと削除。`blacklist:tokens:`（ログアウト = トークン単位。版では表現できない）は存続。自助変更の当該トークン失効は版が覆うため撤去し、変更後は当該端末も再ログインとなる。

### 前提（核実済み）

停止中アカウントの恒常的な拒否は発行経路の enabled 検査が担う: パスワードログインは `DaoAuthenticationProvider`、LINE ログインは連携済み発行口の停止検査が 401 で拒否し、claim 組み立ては単一の発行点に収束していて検査の無い発行口は無い。版が担うのは「発火時点で生きていたセッションの即時失効」だけである。

## 帰結

- 時刻解釈由来の三つの窓が構造的に消える。TTL は失効の正しさの前提からキャッシュの鮮度上限に格下げされ、`APP_JWT_EXPIRATION_MS` の稼働中変更が失効の正しさを壊さなくなる。
- 定常時の検証コストは毎要求 Redis 最多 3 回 → 2 回（token ブラックリスト + 版の GET）、DB は 0 回のまま。miss 時のみ標量投影 1 本（利用者ごと TTL 窓あたり最多 1 回）。キャッシュ書き漏れの最悪は旧トークンが TTL まで延命することで、commit 後直登録の例外顕在化（500）で運用が気付く — 現行ブラックリストと同じ位置づけ。
- 挙動変更が二つ、いずれも安全側: 自助変更で全端末が失効する（従来は当該トークンのみ）。再開しても停止前のセッションは復活しない（従来は復活した）。
- `AuthSessionService` はイベントが運ぶ確定版を commit 後に反映する。再開側は版を戻さないため、旧方式の REQUIRES_NEW 再読ガードは持たない。

## 追補: 版更新と通知の責務境界

2026-09-12 採用（[#878](https://github.com/kanghouchao/Kizuna/issues/878)）。この追補は実装予定の規範であり、実装完了を示さない。

- user の application 層の統一操作が、停止・パスワード変更・明示的な全セッション失効の集約行為とイベント発行を束ねる。増版は集約内に残す。停止済みへの停止再要求は増版せず、人には現在版を再通知する。commit 後の Redis 更新失敗から再要求で回復できるため、通知は状態差分でなく要求に従う。
- 統一操作の具体クラスだけを型単位の `@NamedInterface("credential-operations")` で公開し、auth は `user::credential-operations` を同期参照する。既存の ActorIdentityService 等と同じ公開方式であり、application 全体の公開や公開のためだけの interface / Impl 分割は不要である。公開面は三操作に限定し、PlatformUser 引数は既存の `user::domain` 境界を利用する。
- SERVICE も初回停止で増版するという ADR 0025 の規則を維持する。セッションを持たない SERVICE への通知は統一操作内の明示分岐で省く。業務サービスに例外を分散させない。
- 統一操作は MANDATORY で業務サービスの既存トランザクションへの参加を要求し、保存・flush は業務サービスに残す。授権変更と停止を含む更新では、先行 flush が既存の制約例外変換を迂回し得るためである。業務変更と版更新は一緒に確定・取消される。
- 既存のイベントと同期受信・手書き afterCommit を維持する。集約へのイベント蓄積や repository による自動発行を導入せず、user から auth の失効サービスへの直接依存も作らない。
- 通知規則は統一操作の契約テストに集め、既存の認証・キャッシュ検証を存続させる。ArchUnit で集約の三つの行為の呼出と失効イベント構築を統一操作に限定する。
