# 応募者添付の非公開ストレージは独立した実例とし、基盤が宣言し、意図してバックアップしない

Status: Accepted（裁定は #1130、2026-10-30）

## 決定時の背景

応募者添付（JPEG / PNG を再符号化した副本）は連絡先と同等の個人情報で、公開バケットへの保存は避ける設計と GLOSSARY が定めている。本番は単一ホストの docker compose で、S3 は自前の SeaweedFS が一つだけ動き、公開バケット `uploads` は backend が起動時に作成して匿名読み取りの policy を付け、Traefik が `/static` をそのまま転送している。非公開の保存先をこの構成のどこに置くか、誰がバケットを作るか、保持期間による削除とバックアップをどう両立させるかを決める必要があった。

## 決定

- **非公開ストレージは公開とは別の SeaweedFS 実例 `private-storage`** とする。独立したボリュームを持ち、Traefik のルートもホストポートも持たず、compose の内部ネットワークからだけ届く。development と release の両方に置く。
- **非公開バケットは compose が宣言する**（`-bucket=applicant-images`）。backend はバケットを作らず、起動時に存在と policy が一つも無いことを確かめる。
- `enabled=true` のとき、隔離検査（endpoint・バケット名・資格情報が公開側と異なる）、バケットの存在、policy の不在のどれかが満たされなければ **backend は起動に失敗する**。黙って 503 に落ちない。
- **非公開ボリュームはバックアップしない。**

## 理由

- 同じ SeaweedFS に二つ目のバケットを足すだけでは、公開 policy の付け間違い一つで添付が匿名に読める。別の実例にして外から届かないネットワーク構成にすれば、拒否が policy の正しさに依存しない。同じ実例で別ポートの S3 ゲートウェイを立てる案は filer とメタデータを共有し、隔離がゲートウェイ層に留まるので退けた。外部のマネージド S3（AWS S3 / R2）は耐久性で勝るが、初めてのクラウド契約・課金・外部資格情報の管理を持ち込むので退けた。
- 公開バケットは backend の起動処理が作成と匿名読み取りの policy 付与を行う。非公開バケットを同じ経路に載せると、起動時に保存先の状態を書き換える口が非公開側にも生まれる。基盤が宣言し backend は確認だけにすれば、backend が policy を書く経路は公開側にしか存在しない。
- 匿名化は添付の実体を削除する。バックアップがあれば削除済みの添付が世代の満了まで残り、保持期間を越えて個人情報を持ち続ける。添付は再符号化した副本で証拠保全ではなく、失っても応募者の行と選考記録は DB に残るので、喪失の代価を受け入れる。

## 帰結

- ディスク障害で非公開添付は失われうる。運用手順書にその旨と理由を明記する。
- 原本の証拠保全を扱うことになれば、保全対象についてはバックアップの是非を改めて決める必要がある。
- 資格情報のローテーションは `private-storage` と backend の同時再起動で行い、その間の数秒は添付機能が 503 を返す。
- 保持期間が未設定だと匿名化は何も起こさず、添付は無期限に残る。本番での有効化は保持期間の設定を前提とする。
