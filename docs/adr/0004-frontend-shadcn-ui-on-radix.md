# フロントエンドの UI 基盤は Radix ベースの shadcn/ui を vendoring する

Status: Accepted

## Context

管理画面の UI は、手書きのマークアップと Headless UI のコンポーネントが混在した状態で育ってきた。
同じ見た目の要素が画面ごとに別々のクラス列で書かれ、モーダルやドロワーは節ごとに寸法・余白・境界線を
手で指定していた。配色も Tailwind の生パレットクラス（`bg-gray-50` / `text-gray-900` / `border-gray-200` 等）を
直接書く方式で、admin 画面全体で千数百箇所に達していた。

ここへダークモード対応の要件が加わる。生パレットクラスは明暗の切り替えを表現できないため、対応するには
全箇所に `dark:` 変種を書き足すことになり、画面数に比例して負債が増える。加えて、生クラス方式では
「この緑は状態を表す成功色なのか、単なる装飾なのか」が markup から判別できず、機械的な置換もできない。

UI ライブラリの選定にあたっては、shadcn/ui の既定 base が Base UI へ切り替わった一方で Radix も
引き続きサポートされること、既存の Headless UI からの移行コスト、コンポーネントをコードとして自リポジトリに
取り込む vendoring 方式の是非を調査した。その上で、配色パレット・主色・角丸・ダークモードの実現方式・
ファイル配置とインポート経路について、それぞれ個別に裁定を行っている。

## Decision

shadcn/ui のコンポーネントを `frontend/src/shared/ui` へ vendoring する。base は Radix とし、
個別パッケージではなく統合パッケージ `radix-ui` を使う。

- **トークン層**: `src/app/globals.css` の `:root` / `.dark` に oklch 値を定義し、`@theme inline` で
  Tailwind のカラーユーティリティへ公開する。基調は zinc、主色は blue-600、角丸は 0.5rem。
- **ダークモード**: `.dark` クラス方式を `next-themes` で駆動する。
- **意味色**: 状態を表す語彙は destructive / success / warning の 3 種に限る。danger は destructive と
  同義になるため独立したトークンを立てない。単一の消費者しか持たないドメイン固有色は専用トークンを作らず、
  既存トークンの派生で表現する。
- **配置と参照**: ファイル名は kebab-case、外部からの参照は `@/shared/ui` のバレル経由に統一する。
- **生成物の扱い**: 取り込んだコンポーネントは無改変で保持し、prettier による整形のみ適用する。
  画面ごとの差異は消費側の `className` で吸収する。

## Consequences

管理画面の実装規約は `frontend/DESIGN.md` が正本となる。どのプリミティブを使うか、旧クラスから
トークンへどう写像するか、フォームの配線をどうするかはそちらに集約し、本 ADR は基盤の選択だけを扱う。

生成物を無改変で保つ方針により、プリミティブの見た目を変えたい要求は「消費側で `className` を渡す」か
「トークンの値を変える」かのどちらかに倒れる。前者は影響範囲が閉じ、後者は全画面に一様に効く。
どちらでも表現できない要求が出た場合のみ、生成物への追従方針を改めて検討する。

トークンは意味の名前で参照されるため、明暗の切り替えは各画面を編集せずに追随する。逆に言えば、
生パレットクラスが 1 箇所でも残っていればその箇所だけダークモードで破綻する。この負の不変量は
画面単位の移行が完了するまで満たされない状態が続き、移行途中の画面が混在する期間が発生する。

Headless UI は撤去済みで、依存としても残っていない。公開店舗フロントは独自のテンプレート別
トークン体系を持ち、本 ADR の対象外である。認証系画面も専用のスタイルシートによる別の視覚世界として
扱い、管理画面のトークン契約には従わない。

プリミティブの追加は shadcn の CLI による生成とバレルへの追記で行う。並列に進む移行作業がバレルを
同時に編集して競合しないよう、必要になるプリミティブは実際の消費者を確認した上で先にまとめて供給する。
