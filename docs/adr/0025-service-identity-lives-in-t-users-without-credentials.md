# サービスID は資格情報を持たない PlatformUser として `t_users` に同居させる

Status: Accepted

## 決定時の背景

人の共用資格情報では、無人処理と担当者の責任・停止単位が混ざる。一方、サービスIDを別表にすると既存 actor FK と授権語彙が二重化する。PlatformUser に同居させ、ログイン禁止を運用慣行でなく資格情報を持てない構造で表す。

## 決定

- **サービスID は `UserType.SERVICE`、行は `t_users` に同居させる。** 別表を建てない。授権は STAFF と同じ
  「ロール × 店舗集合」で、専用の授権語彙も持たない。各所の actor 列は既存の外部キーのまま SERVICE の id を受ける
  — **actor 列の血統が単一**であることが、この決定が守る第一の性質である。
- **資格情報を持たないことは構造上の事実にする。** `t_users.email` / `password` の NOT NULL を外し、ドメイン不変条件を
  「SERVICE は両列とも null、他の種別は両列とも非 null」と**双方向**で置く。SERVICE に email を持たせようとする
  構築・パスワード変更はドメイン例外で拒否される。列の一意制約（`uq_t_users_email`）は残す — PostgreSQL の一意制約は
  複数の NULL を許すので、資格情報を持たない行が何行あっても一意性は成り立つ。
- **拒否は二層。** 第一層は上記の不変条件（照合できる値がそもそも行に無い。email で引く認証経路は SERVICE に到達
  できない）。第二層は `PlatformAuthService.issueTokenFor` の種別守衛で、パスワードログインと LINE ログインが
  共有する**唯一のトークン組立点**に置く（ADR 0024 が依拠する「第二の組立経路を作らない」不変量の再利用）。
  認証手段が増えても拒否が片方の経路だけ抜け落ちない。
- **拒否の観測面は資格情報の不一致に揃える。** 守衛の例外は `BadCredentialsException` を継承し、応答は
  「メールアドレスまたはパスワードが正しくありません」で 401。別の型・別の文言にすると、応答の違いが
  「この身分はサービスIDである」ことの存在オラクルになる。
- **停止は行を残す（`enabled=false`）。** 削除しないのは、過去の記録が指す実行主体を後から辿れるようにするため。
  停止が資格情報の版を進める挙動（ADR 0022）は SERVICE でも無害で、特例を設けない — 版は将来サービスIDが
  トークンを得る形（#395）になったときそのまま効く。
- **スタッフ管理面には現れない。** 人のアカウント管理・管理者管理・店長設定・店舗スタッフ管理の四面は本人種別
  STAFF で絞っており、SERVICE は構造的に対象外である。ロールを持つかどうかの述語（`UserType.holdsRoles()`）は
  授権専用で、この四面の対象判定には使わない。

## 帰結

- **サービスIDは対話ログインできない — 規約ではなく、照合する値が無いから。** 資格情報を要求する経路を後から
  追加しても、行に値が無い限り成立しない。
- **第二層の守衛は真の経路からは到達不能である。** email が null の行は認証経路が引けないため、守衛の単体テストは
  「email を持つ SERVICE」を mock で組んで突く。テストを通すために第一層を緩めることはしない — 緩めた時点で
  「構造上の事実」という決定そのものが失われる。
- **資格情報の 2 列が NULL 可になり、DB は種別ごとの要否を強制しない。** 守衛はドメイン不変条件だけになる。
  CHECK 制約で表す道もあるが、種別と 2 列の関係は集約の不変条件として既にあり、二重に持つと片方だけ更新される。
- **管理面・`SERVICE_ID_MANAGE`・既定ロール授与の禁止・実行框架は本 ADR の射程外**（後続チケットと #395）。
  本 ADR が定めるのは器と、資格情報を持たないことの表し方だけである。
