# キャストの正本を本人・店舗在籍・公開プロフィールに分離する

キャストの同一人物性は店舗を跨ぐ一方、在籍は入退店ごとの区間であり、展示物と内部情報は公開境界が異なる。Cast（本人）、CastEnrollment（店舗在籍）、CastProfile（公開プロフィール）を別集約とし、それぞれの意味の値を一箇所だけに保持する。裁定は #383・#850〜#856、構造の実装は #859。

## 同一性と参照

Cast はプラットフォームアカウントとの必須・一意 FK で結ぶ本人で、本名と生年月日のみを追加属性とする。招待受諾時に作成または解決するため、店舗が在籍を先行作成した時点では CastEnrollment.cast_id は空でよい。受諾前でも店舗内の運営は可能である。

CastEnrollment は StoreScoped のエピソード行で、再入店は新行となる。有効在籍は一人一店最大一件で、`status <> 'WITHDRAWN'` の部分唯一索引で保証する。受諾の索引衝突は 409 に写し、招待のクレーム・本人紐づけ・店舗集合の変更を同じトランザクションで巻き戻す。

受注・申請・シフト・実績・招待は在籍 ID を参照する。本人 ID を参照すると引用鎖が店舗境界の外へ出るため採らない。店舗 API の既存 `cast_id` も在籍 ID を指す。本人ポータルは認証済みユーザーから本人と在籍 ID 集合を解決し、その集合でシフトと申請を絞る。

## 公開と内部情報

源氏名と展示項目の正本は CastProfile で、在籍と 1:1 に結ぶ。内部画面も同じ源氏名を読む。公開の既定は UNPUBLISHED、露出条件は PUBLISHED ∧ ENROLLED である。公開取得は profile を選択し、在籍状態を条件としてのみ使う。公開応答の型に在籍状態・監査日時・本人属性を持たせない。

内部 custom fields は enrollment、公開 custom fields は profile に格納する。定義の is_public は作成時固定とする。定義を削除すると現行値も除去し、同名キー再作成で値を復活させない。定義の変更・削除と値編集は店舗行の FOR NO KEY UPDATE を先に取得して直列化する。公開状態の変更は内部情報のスナップショット記録の対象ではない。

## 取引と削除

招待受諾のロック順は店舗 → 在籍 → 招待 → ユーザーを維持する。既存ユーザー行の排他ロックを得てから本人を resolve-or-create するため、同一ユーザーの跨店並行受諾も本人行を二重作成しない。

店舗削除は在籍と公開プロフィールへ連鎖するが、本人は残る。在籍からの注文・実績の削除拒否を維持する。本人とユーザーは NO ACTION の FK で保護し、紐づいた在籍を暗黙に削除しない。

履歴二表は最終形で宣言する。状態操作・履歴記帳・照会は #860、招待前提の業務的完備は #861、管理 UX は #862、プラットフォーム跨店照会は #863 が担う。報酬とサービス提供可否は三層に追加しない。

## 開発環境への適用

Liquibase baseline を直接変更する。integration・E2E は空の一時 DB で検証する。適用済みの永続開発 DB は backend イメージを再構築した後、[DB 再作成手順](../../backend/src/main/resources/db/AGENTS.md#after-editing-the-baseline-the-dev-db-must-be-recreated)でデータベースを再作成する必要がある。ボリュームは削除しない。
