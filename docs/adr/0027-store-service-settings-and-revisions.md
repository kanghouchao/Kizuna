# 0027: 店舗サービスの条件と歴史版本をサービスモジュールに保存する

日付: 2026-09-14

## 決定

店舗のコース・特殊サービス・加算は service モジュールの ServiceItem が所有する。名称・時間・価格・固定報酬を ServiceTerms にまとめ、種別に応じた制約を集約で強制する。設定と受注の約定は別の正本であり、Cast・CastEnrollment・CastProfile に設定や報酬を追加しない。

現在値と追記型 ServiceRevision を同一トランザクションで保存する。歴史版本は項目内で 1 から増え、JPA の楽観ロック版とは分離する。同値保存では版本を増やさない。変更・削除は行ロック下で要求の版本を照合し、古い内容を見た操作者による上書きを拒否する。

削除は deleted 標記と削除版本の追記で表す。現在値と歴史版本を物理削除せず、削除済み一覧から履歴に到達できる。歴史版本には変更前後の条件、操作者 ID、日時を保持する。項目・店舗の複合 FK が店舗を跨ぐ歴史行を防ぎ、店舗・操作者の削除も記録の連鎖消失を起こさない。

設定の全操作と履歴照会には SERVICE_MANAGE を要し、STORE_MANAGER のみに既定授与する。店舗自作ロールへの委譲を許す。ORDER_MANAGE 単独と通常 HQ は設定管理の口を操作・照会しない。受注用のコース・加算候補は ORDER_MANAGE、訂正用の歴史版本は ORDER_MANAGE と ORDER_CORRECT で照会する。

## 理由

現在値だけを上書きすると、削除や改定後に過去の条件を説明できない。一方、現在値を履歴から毎回再構成する必要はないため、設定の現在値と不変の前後値を併記する。業務版本を JPA 版から分けることで、保存・変更・削除の意味に沿った番号と一意な履歴順を保つ。

## 境界と結果

設定は即時適用で、未来日・遡及有効期間や平台共有項目を持たない。本人受諾はサービス側の ServiceConsent と追記型 ServiceConsentEvent に保持する。コース・加算は受注の候補選択と歴史版本採用に接続し、受注側に採用条件を保存する（ADR 0018・0019）。特殊サービスの受注適用と給与連携は後続票である。

一覧は Page、増加する履歴は項目内で一意な版本の降順 CursorPage とする。店舗 filter と認証済み HTTP / PostgreSQL の検証を共用する。スキーマは pre-launch baseline を直接更新し、既存環境への互換層・移行経路は持たない。


## 本人の提供意思

本人 API は認証主体から当該店舗の有効在籍を解決し、その店舗 filter 下で条件を読む。Cast・CastEnrollment・CastProfile に意思を追加しない。本人画面の応答には他人の情報や設定担当者の属性を含めない。

設定の revision_number と条件の terms_version を区別する。名称のみの変更では条件版を保持し、時間・価格・報酬・有料無料区分の変更で進める。受諾時の条件版と設定版本への参照を保存することで、旧条件への受諾と条件改定と能動的拒否を区別する。意思は未登録・受諾・拒否で保持し、受諾した条件版と現行版が異なる場合に再受諾待ちを表示する。拒否は条件改定でも拒否のままとする。

設定改定・退店・本人操作は店舗行の FOR NO KEY UPDATE を先頭に取得する。本人操作はその後に現行在籍・条件版・意思版を照合し、競合時は意思と履歴の保存をともに拒否する。退店済み在籍を現在の提供資格から除外し、再入店の新在籍には旧意思をコピーしない。設定・在籍・本人履歴への FK は NO ACTION とし、追跡記録を暗黙削除しない。
