# 終端状態の受注は書き換えず、行も削除しない

Status: Accepted

## Context

汎用更新 `PUT /store/orders/{id}` は状態を見ずに内容を書き換える。`Order#apply(OrderPatch)` に状態の
判定が無いため、**完了済みの受注でも**到着予定時刻・人数・コース時間・延長・オプション・割引名・手動割引・
備考・キャストへの伝言が書き換わり、指名と受付担当も差し替えられる。唯一の守衛は「status を COMPLETED へ
動かせない」ことだけで、キャンセル済みには守衛そのものが無い。受注には変更履歴が無いので、これらの
書き換えは**誰が・いつ・何を**のどれも残さない。

確定後の取消も同じ口の status 遷移が唯一の経路で、専用の操作・確認・理由のいずれも無い。さらに
`DELETE /store/orders/{id}` はポイント台帳の仕訳が参照する COMPLETED と未確定の申請だけを撥ねるため、
**確定済み・取消済みの受注は行ごと硬削除できる**。

この状態は #380（受注の拡張 spec）の**先行形ではない**。#380 の要件 4 は「権限のある利用者は完了後も
金額・内訳を訂正でき、**訂正が記録される**」であり、現行の穴は権限（ORDER_MANAGE は受注を扱う全員が
持つ）も記録も伴わない。加えて #380 の要件 3 が「内訳と合計が照合できる」を導入した時点で、割引名・
手動割引だけが後から動く現行の形は記録の不整合から照合の破れへ悪化する。

一次資料の調査（#684、10 製品）では、編集にロックがかかる位置は (a) 会計完了時点（Fresha の Completed は
以後変更不可）と (b) 外部チャネル由来の予約への期限（レストランボード）の二つが典型で、自店入力の予約は
来店後もステータス修正が広く許される。本システムで (b) に当たるものは無く、(a) は完了＝ポイント記帳・
帰属記録の成立と不可分という本システムの構造と一致する。

本仓には既に、不可逆な操作の作法が二つ確立している。ひとつは専用 POST + 理由必須（帰属記録の無効化）、
もうひとつは二度目を静默冪等に委ねず明示的に撥ねること（`Order#completeWith`、`OrderAttribution#invalidate`）。

## Decision

- **汎用更新は終端状態（COMPLETED / CANCELLED）を受け付けない**。これは #380 が退けた「財務ロック」の
  新設ではなく、記録を伴わない裏口を閉じる措置である。完了後の内容訂正は #380 の権限付き・記録付きの
  専用経路が担い、本 ADR はその形を先取りしない。
- **判定は「終端か」という単一の述語で行い**、状態ごとに守衛を書き分けない。書き分けは同じ規則を
  二箇所に持たせ、片方だけが更新される入口になる。
- **確定後の取消は専用の操作とし、定義域は `CONFIRMED → CANCELLED` のみ**。誤って完了した受注の
  救済にこの操作を広げてはならない。帰属記録の無効化を代用にすることも既に禁じている（CONTEXT.md
  受注帰属記録 の _Avoid_）ので、誤完了の救済は #380 が定めるまで存在しない。
- **取消は理由を必須とし、実行者と時刻を残す**（形は帰属記録の `invalidated_reason` / `invalidated_by` /
  `invalidated_at` に揃える。実行者は書き込み時必須・読み出しでは FK の SET NULL により欠落しうる）。
  未確定申請の謝絶が理由を持たないのは、店舗がまだ受諾していない段階だからで、既に受諾し確定シフトと
  客への約束を消費した後の取消とは重さが違う。**この理由は分類軸ではない** — 「客都合/店都合/無断」の
  ような集計可能な分類が要るようになったら列を足すのであって、情報の足りない今それを enum で固めない。
- **二度目の取消は撥ねる**。`Order#transitionTo` の静默冪等に委ねると、初回の理由と実行者が黙って
  上書きされ、理由を必須にした意味が消える（`OrderAttribution#invalidate` と同じ理由）。
- **受注 1 件を名指して消す口は廃止する**。理由必須の取消を立てながら無痕の硬削除を残すことは、
  理由の必須を制度上の任意へ落とす。誤登録も行を消さず取消として残す。店舗ごと廃棄する経路
  （店舗削除の連鎖）はこの決定の対象ではない — Consequences を見よ。
- **汎用更新から `status` を撤去する**。上記の後、この口に残る合法な状態遷移は無い（CREATED は会員申請
  専用でその遷移は確定・謝絶が独占し、CONFIRMED → COMPLETED は完了処理が、CONFIRMED → CANCELLED は
  取消が独占する）。**前提として #680 の「店舗起点の受注は確定で出生」が先または同時に落ちている必要が
  ある** — 出生が CREATED のままこの撤去を行うと、店舗が起こした受注が確定へ到達できなくなる。

## Consequences

- **完了後に記録を直す手段は #380 まで存在しない**。凍結されるのは `OrderPatch` の全項目 — 到着予定
  時刻（開始・終了）・人数・コース時間・延長・オプション・割引名・手動割引・備考・キャストへの伝言 —
  に加え、汎用更新が扱う指名と受付担当である。会計金額・利用ポイント・自動付与ポイントは元から
  完了処理でしか書けないので、ここで新たに失われるものではない。
- **「取消率」の集計は誤登録を含む**。分類軸を足すまで切り分けられないが、記録を消して統計を綺麗に
  見せる方を採らない。
- **受注の行が消える経路は 1 つ残る — 店舗の削除である。** `fk_t_orders_store` は `ON DELETE CASCADE`
  で、`StoreRegistryService#delete` が塞ぐのは稼働中の店舗と、完了済み受注またはポイント仕訳を持つ
  店舗だけ。開店前の店舗に確定・取消の受注しか無ければ、店舗ごと消える。ADR 0006 / 0012 はその連鎖に
  明示的に依拠しているので、本 ADR はそれを変えない。ここで廃止するのは**受注 1 件を名指して消す口**
  であって、店舗という上位の単位ごと廃棄する操作ではない（その可否は #632 の裁定が持つ）。
- **既存の CANCELLED 行は理由・実行者・時刻を持たず、後から復元もできない**（受注は状態変更の履歴を
  持たない）。移行の形は定めない — 本システムは未稼働で、#680 裁定 3 が既存データを移行せず廃棄すると
  既に決めているためである。稼働後に同じ状況が生じたなら、そのときは別の裁定が要る。
- 会員本人へ返す `MemberOrderResponse` は項目の白名単なので、取消理由は店舗内部に留まる。会員へ
  見せる判断が要るなら明示的に追加する操作になる。
- **二度目の取消は、順に届けば 400・同時に届けば 409 になる。** 順に届いた 2 度目は集約の守衛が
  撥ねて 400。同時に届いた 2 つは双方が `CONFIRMED` を読んで守衛を通り、`BaseEntity` の `@Version`
  による楽観ロックで敗者が `ObjectOptimisticLockingFailureException` → 409 に落ちる
  （`CommonExceptionHandler`）。画面の確認ダイアログと送信中の抑止が塞ぐのは前者だけで、別のタブや
  別の端末からの同時取消は後者になる。敗者に `CANCELLED` を観測させたければ行を押さえて直列化する
  形もあるが、本 ADR はそこまで求めない — 記録される理由と実行者は先に commit した側のものであり、
  敗者を黙って成功させる方が「自分の理由が残った」と誤って伝える。
- 汎用更新から状態遷移が消えることで、`OrderServiceTest` の status 系 6 件は作廃または観測面の移設に
  なる。「取消できること」と「不正な遷移が撥ねられること」の 2 件は移設であって削除ではない。
