# フロントは画面遷移の守衛を持たず、本人の種別と権限を GET /me から読む

Status: Accepted

フロントは Next の proxy にも各エリアのシェルにも画面遷移の守衛を置かない。未ログインは最初の API 応答の 401 を全域の 401 経路が拾い、ログインへ差し戻して会員の戻り先（フラグメントを含む）も預ける。データの隔離と認可はバックエンドが fail-closed に担っており、守衛は体験の層にすぎず、401 経路と重複していた。セッション種別とエリアが食い違う直打ち（キャストのセッションで /admin を開く等）は差し戻さず、画面に 403 が出ることを受け入れる。

フロントは JWT の payload を解読しない。本人の種別・権限・メールアドレスは従業員の管理画面のシェルが搭載する `GET /me` の応答から読み、保存はせず layout の生存期間だけ保持する（再読込で取り直す）。取得が済むまで権限で出し分ける操作は出さない。`GET /me` の権限は DB から引く。権限の実効値（DB）とトークンの `authorities` の乖離は、実効権限が変わった利用者の資格情報の版を増分して再ログインさせることで閉じる（ADR 0022）。

## 検討した選択肢

- proxy に守衛だけ残す: ちらつきが無いが、キャスト・会員のシェルの守衛と同じ規則が二箇所に並び、401 経路とも重複する。
- 各エリアの Server layout で `redirect()`: layout はクライアント遷移で再描画されずチェックが毎回は走らず、戻り先 cookie も書けないため不採用。
- JWT の payload を読み続ける: トークンと原子的に切り替わる利点はあるが、権限の出所がトークンと `GET /me` の二つになる。
- `GET /me` の結果をログイン時に localStorage へ保存: トークンを書く全経路での同期・ログアウト時の消去・タブ間の食い違いを抱えるため不採用。

## 帰結

- 未ログインで開いた画面は、401 が返るまで一瞬シェルが描画される。
- 全画面の再読込ごとに `GET /me` が 1 回走る。
