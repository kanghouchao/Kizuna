# 当日実績はシフトと別の集約であり、実績に参照されるシフトは削除できない

Status: Accepted

## Context

#379 要件 3 は当日実績（実際に出勤した事実）の一等記録化を要求するが、現行実装には予定（`t_shifts`）
しかなく、実績という概念そのものが無い。記録の形として「シフト 1 個の scheduled → worked 状態遷移」と
「予定と実績の別集約」の二案が成り立つ。

業界一次資料の調査（#721、Deputy / When I Work / UKG / KING OF TIME）では、主要 WFM 製品は例外なく
予定（シフト）と実績（タイムシート/勤務データ）を別リソース・別集約として持ち、予実照合（遅刻・早退・
欠勤）は保存せず導出として扱う。シフト 1 個の状態遷移で実績を表す製品は見つからなかった。実績は訂正と
いう予定と異なるライフサイクルを持ち、法定保存（労基法 109 条: 保存 5 年・当分の間 3 年）が掛かるのも
実績側だけである。

受注確定の内部検証（hasConfirmedShift）は当日の確定シフトを要求する（CONTEXT.md「指名 / 指名候補」）。
実績の導入がこの検証の意味を変えてはならない。

## Decision

- **当日実績は `t_shifts` と別集約の一等記録とする**。実績行はキャスト・店舗・営業日（business_date と
  して物化）・実際の開始/終了時刻・待機場所を持つ。実際終了は閉店時記入まで NULL 可。
- **確定シフトへの参照は可空の `shift_id`** とし、1 シフトにつき実績は最大 1 行（部分一意）。予定なしの
  飛び込み出勤は shift_id = NULL の一等記録であり、「予定外の出勤か否か」が照会可能な事実になる。
- **実績行（取消済みを含む）が参照する限り、シフトの削除を拒否する — RESTRICT 語義**。SET NULL は
  「予定通りの出勤」を「飛び込み出勤」へ不可逆に偽装するため採らない。DDL は NO ACTION で宣言し、
  4xx は応用層守衛が出す（PG は RESTRICT 違反（SQLSTATE 23001）に制約名を付けず、DbConstraint 写像が
  効かない）。
- **実績は物理削除しない**。誤建行は取消標記（論理削除）とし、導出・照会から除外する。訂正は就地更新と
  同一トランザクションで訂正履歴表へ「編集前の行スナップショット・訂正者・時刻」を書く。
- **未取消の実績が付いたシフトは work_date を変更できない**。実績は記録時に business_date を物化して
  おり（予実は常に同一営業日）、事後の日付変更はこの不変量を破る。時刻・status の直接編集は実績の有無と
  無関係に維持する。逃げ道は既存機構で足りる: 実績を取消標記 → 日付を変更 → 再記録（全て履歴に残る）。
- **欠勤は行を建てず導出する**（確定シフトあり・実績なし）。実績行の存在そのものが出勤確認であり、確認
  フラグ・状態機械は持たない。

## Consequences

- 「真の欠勤」と「記録漏れ」は区別できない。明示欠勤が必要になれば status 列（既定 WORKED）を互換
  migration で足す。
- 誤って建てたシフト・実績の組は削除できないが中性化できる: 実績を取消標記し、シフトを TENTATIVE へ
  落とす（hasConfirmedShift・公開・欠勤導出のいずれからも外れる）。実績なしシフトの削除は従来通りで、
  `t_shift_requests.shift_id` の SET NULL も不変。
- 予定側は編集の全史を持たない（実行主体は行に印字される最後の一手のみ）。編集全史の保持は法定保存対象
  である実績側だけが担う。
- （キャスト・店舗・営業日）につき実績は 1 行。一日二枠の実需が出たら制約を緩め、中抜けは訂正で区間を
  まとめる。
- 予実照合（遅刻・早退・欠勤）は保存せず、予定と実績の突合から都度導出する。
