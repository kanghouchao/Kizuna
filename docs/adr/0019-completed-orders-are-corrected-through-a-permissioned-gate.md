# 完了した受注は権限付きの門でだけ訂正でき、訂正前の姿が痕として残る

Status: Accepted

## Context

[ADR 0013](0013-terminal-orders-are-frozen-and-never-deleted.md) は汎用更新から終端状態を締め出し、
「完了後の内容訂正は #380 の権限付き・記録付きの専用経路が担う」「誤完了の救済は #380 が定めるまで
存在しない」と予告した。[ADR 0018](0018-order-fees-are-lines-and-the-total-is-derived.md) も、完了処理が
書いたポイント利用の行を直す経路が無いことを「完了後訂正の門が建つまでの既知の欠落」として残している。

#380 の要件 4 は「権限のある利用者は完了後も金額・内訳を訂正でき、訂正が記録される」「終了時刻の入力は
業務上の完了であり財務ロックではない」である。一次資料の調査（#747）では、支払済みの記録に対する
業界慣行は**追記型訂正** — 内容を直し、状態は動かさず、訂正の痕を残す。

本仓には痕の先例が 2 つある。ひとつは当日実績（`Attendance` / `t_attendance_corrections`）の
**就地更新＋訂正前スナップショット行**、もうひとつは取消・帰属無効化の**専用 POST ＋ 理由必須**である。

## Decision

- **救済の深さは内容訂正まで**。COMPLETED → CONFIRMED の回退は開けない。回退は帰属記録（ADR 0009 の
  完了時固化の不変事実）・台帳仕訳・自動付与の三機構に逆操作を新設することになる。「客が来ていないのに
  完了した」級の誤完了は既存機構の連鎖で救済する — 明細行の清零＋帰属記録の無効化＋ポイント訂正
  （ADR 0012）。金額零の COMPLETED 行が残るのは受容する。
- **対象状態は COMPLETED のみ**。CANCELLED は門の外で、取消理由の訂正も開けない — ADR 0013 が二度目の
  取消を明示拒絶して守った初回理由・実行者の保護を、訂正口で迂回させない。誤取消（実際は来店していた）の
  救済は**同内容で受注を起こし直す**こと（店舗起点の受注は出生即 CONFIRMED なので支障は無く、旧行は
  誤操作の痕として残る）。
- **直せるのは三組だけ** — 受注明細行（POINT_REDEMPTION を除く七種の追加・修正・削除。`total_fee` は
  集約が再導出）、実績時刻（`actual_arrival_time` / `actual_end_time`）、コーススナップショット
  （`course_name` / `course_minutes` / `extension_minutes`）。**それ以外（予定時刻・人数・指名・受付担当・
  備考・キャストへの伝言）は ADR 0013 の凍結のまま**で、指名は将来の給与計算へ波及するため特に動かさない。
  金額行とコース快照を対で直せるのは、金額だけ直って名称・分数が残る半修状態を作らないためである。
- **凍結は要求の型で表す**。`OrderCorrectionRequest` に凍結字段の項目を持たせず、未知の項目を撥ねる設定
  （`fail-on-unknown-properties`）がそのまま 400 にする。サービス層に項目ごとの拒否リストを持たせない。
- **POINT_REDEMPTION 行は門内でも編集不可**。台帳の減算仕訳と対で書かれた記録であり、ポイント利用の
  誤りはポイント機構（ADR 0012 の訂正・手動調整）経由で直す。門が扱うのは店舗手入力の七種だけである。
- **権限は新設の `ORDER_CORRECT`**（Console.STORE・初期配点 STORE_MANAGER。先例 POINT_ADJUST）。
  `ORDER_MANAGE` は受注を扱う全員が持つ日常権限であり、それで門を守ると #380 の「権限のある利用者のみ」が
  空文になる（ADR 0013 の Context が名指しした穴）。
- **入口は専用端点 `POST /store/orders/{id}/corrections`（201）で、理由必須**。汎用更新は終端状態を
  受け付けないまま（ADR 0013 不変）。理由は凍結済みの記録を動かす特権操作の根拠であり、取消理由と同じく
  **分類軸ではない**。
- **要求は三組の全量を運ぶ**（省略は「変更しない」ではなく「値なし」）。実終了時刻・延長分数を空へ戻す
  訂正が要るため、部分更新の形では表せない — 当日実績の訂正要求と同じ作法である。
- **痕は就地更新＋訂正前快照行**（`t_order_corrections`。1 回の訂正＝1 行）。標量前値（実績時刻 2 列・
  快照 3 列・`total_fee`）は列で、行に同一性の無い明細の前値は**行集合全体の jsonb 写し**で持つ。
  `corrected_by`（書き込み時必須・FK SET NULL で読み出しでは欠落しうる）＋ `corrected_at` ＋ 理由。
  快照は訂正を当てる**前**に起こす（管理下の集約はその場で書き換わる）。
- **零自動波及**。門はポイント台帳へ一切書かない。完了時の自動付与の語義を「**完了時点の合計に基づく
  時点事実**」と釘打ちし（ADR 0009 と同族）、訂正で合計が変わっても付与は追随しない。訂正後の付与差額は
  応答が返し、差額の手当ては既存機構（POINT_ADJUST の手動調整、誤帰属なら ADR 0012 の訂正）へ案内する。
  訂正者と調整者はどちらも STORE_MANAGER なので権限の断層は無い。
- **付与差額の基準はポイント利用を除いた総和**（ADR 0018）。`total_fee` はポイント控除後の請求額なので、
  それを基準にすると同じ会計がポイントを使うほど付与も減る。完了処理と訂正後の再計算は同じ 1 本
  （`Order#grantBasisAmount`）を読む。

## Consequences

- **受注側の痕は前値の鎖までで、訂正仕訳の横断形式は #386 の領分**（境界宣言）。ある訂正の「後値」＝
  次の訂正の「前値」または本体の現値なので、前後の合計は鎖から導出できる。#386 は将来この快照行から
  取材して接続でき、受注側で仕訳を先取りしない。
- **実績時刻はこの門が唯一の書き込み口になる**。列は以前から存在したが書き込み経路が無く、読み口にも
  出ていなかった。訂正画面が現値を示せるよう `OrderResponse` へ 2 項目を追加した。
- **同時に届いた 2 つの訂正は、双方が COMPLETED を読んで門を通り、受注の `@Version` で敗者が 409 に
  落ちる**。逐次なら 2 回とも成立し、痕が 2 行並んで鎖になる。行ロックは足さない — 記録される理由と
  実行者は先に commit した側のもので、敗者を黙って成功させる方が「自分の理由が残った」と誤って伝える
  （ADR 0013 の二度目の取消と同じ紀律）。
- **行が在るのにコース名を空にする訂正は撥ねられる**。基本コース料金の行名称はコース名の写しから採る
  ため、写し元を消すと行が名乗れない（`InvalidOrderFeeLineException` → 400）。全量送信なので、
  コース名を送り忘れた要求はこれに当たる。
- **`ORDER_CORRECT` の新設は既定授権の承認台帳とカウンタ守衛（`PermissionCodeTest` の 2 件・
  `DefaultGrantApprovalTests`・`PlatformStaffManagementIT` の目録件数）の更新を伴う**。権限行の播種は
  enum 宣言からの導出なので、目録行の手書きは要らない。
- **付与差額の基準は台帳から引く**（受注の `auto_grant_points` ではない）。完了時に会員へ届かなかった受注が
  伝票トークンの申領で事後帰属すると、付与は台帳へ入る一方で受注の列は 0 のまま据え置かれる（申領は完了時点の
  会計を書き換えない、が既決）。列を基準にすると差額が付与の全額ぶん膨らみ、過大な手当てを招く。
- **手当ての宛先は帰属記録が持つ会員であり、画面はその会員コードを名指す**（ADR 0012）。顧客詳細の調整口が
  届くのは顧客に今紐づく会員なので、関連の解除・張り替え・伝票の申領で両者は食い違う。宛先を伏せたまま顧客
  詳細へ送ると、無関係な会員を調整しうる。**帰属記録を宛先に取る付与の口は現時点で存在しない** — 既存の
  手動調整は顧客経由で、差し引き（ADR 0012）は減算専用である。両者が食い違う場合の手当ては人手になる。
- **会計金額が変わっていない訂正では差額を示さない**。基準が同じなら付与も同じで、それでも差が出るのは完了後に
  付与設定が変わった場合だけである。完了時点の付与規則を復元する手立ては現時点で無い（保存しているのは規則では
  なく確定額）ので、金額が動いた訂正では設定変更ぶんの差が混じりうる。既知の限界として残す。
- **付与差額を示すのは会員へ帰属した受注だけである**。帰属していない受注の付与 0pt は「少なく付いた
  付与」ではなく「付与が存在しない」であり、差額を出すと宛先の無い手動調整へ誘う（顧客詳細を開いても
  未紐づけ）。画面の判別は帰属記録の有無（ADR 0012 の「訂正の宛先は帰属記録」）で行い、顧客に今
  紐づく会員では判じない。帰属を読めなかったときは案内を出す側へ倒す — 「動くポイントはありません」と
  誤って言い切ると、実際に残った誤付与に気づく機会がどこにも無くなる。
- **完了時に発行された伝票トークンの付与予定額も、訂正には追随しない**。予定額は完了時点の付与規則で
  確定して持つ設計（申領の早い遅いで同じ会計が別のポイントになるのを避けるため）であり、本 ADR の
  「時点事実」と同じ紀律である。したがって訂正後に申領が起きると、申領者には訂正前の会計に基づく
  ポイントが付く。画面は帰属していない受注にその事実を添えるが、**申領はいつ起きるか分からず操作者への
  通知も無い**ので、この差の手当ては申領後に誰かが気づいたときの手動調整になる。
- **訂正履歴の読み口は建てない**。#380 の受け入れ基準は「前値の鎖から履歴が復元できる」までで、それを
  読む画面がまだ無い。要るようになった時点で `t_order_corrections` を宛先に読み口を足す。
