# 操作の受領は一つのモジュールに置き、再送は対象の現在の状態を返す

Status: Accepted

## 決定時の背景

応答を失った書き込みを利用者が安全にやり直せるようにする仕組み（GLOSSARY「操作の受領」）が、モジュールごとに別の形で実装されていた。広告費と報酬は専用の受領表に要求と応答の写しを置き、助言ロックで直列化する。口コミとアンケートは操作台帳に内容の指紋を置き、一意制約の違反を controller で捕まえて別トランザクションで再送を解決する。ポイント台帳は仕訳行そのものに冪等キーを持つ（ADR 0007）。応募者添付と定期処理の実行要求も対象の行にキーを持つ。

同じ不変条件が四つの形で書かれた結果、既に挙動が割れていた。再送に返す内容が写し（広告費）と現在の状態（口コミ・アンケート・定期処理）で異なり、報酬は初回と再送で直列化の経路が違う。受領表に応答の写しを置く設計は、応答 DTO の改名がそのまま保存形式の変更になる（媒体名を媒体 ID に替えた改修で既に起きた）。画面側も五つの画面が「結果不明の操作をいつ忘れてよいか」の表を各自に持ち、互いに矛盾していた。

## 決定

- **受領は一つのモジュールが所有する。** 業務監査（`audit`）と同じ形の独立モジュールが受領表を一つ持ち、公開パッケージを通じて各モジュールが利用する。受領の行は店舗・操作者・操作キーで一意で、操作名・内容の指紋・対象 ID・成立時の不変の事実・記録時刻を持つ。成立時の不変の事実とは、その操作自身が生んだもので対象の現在の状態からは読み直せないもの（成立時の対象の版、操作が採番した ID、コピーした件数など）に限る小さな構造であり、対象の属性や応答の写しは含めない。何を事実として持つかは操作ごとに命令が決める。広告費・報酬の受領表と口コミ・アンケートの操作台帳はこの一表に置き換える。
- **再送は対象の現在の状態を返す。** 受領は応答の写しを持たない。再送を受けた呼出側は受領の対象 ID で現在の状態を読み直し、通常の応答と同じ形で返す。応答のうち操作自身の成立情報（操作の種別・対象・成立時の版・採番した ID・件数）は受領の行の不変の事実から組み、対象の状態だけを現在のものから組む。「再送か否か」は受領に保存せず、今回の照会が受領に命中したかどうかで決まる。再送の読み直しは呼出側が普段行う読みと同じ規則に従う: 取り下げ・停止・取消・論理削除された対象はその現在の状態を返す。受領モジュールが記録する操作の対象は物理削除しない（口コミ・アンケート・広告費・報酬はいずれも取り下げ・取消・論理削除で終わり、物理削除の経路を持たない）ので、受領が命中したのに対象が無いのは不変条件の破れであり、業務拒否（404）ではなく障害として扱う。物理削除される対象を受領モジュールに載せるときは、先にこの規則を改める。受領の行は消えないので、同じキーの再送が初回として実行し直されることは無い。広告費の前月コピーの応答（コピー ID・コピーした件数・成立時の各月の版）はその例で、行や履歴にコピー ID を持たせず受領の事実で復元する。初回応答との字節一致は目的にしない。
- **指紋は内容の要約であって原文ではない。** 命令（sealed command など）が自身の同一性を決める項目から SHA-256 の指紋を作り、受領モジュールは指紋の文字列だけを受け取る。要求 DTO の JSON 全文は保存しない。
- **操作キーのロックをトランザクションの最初に取る。** 受領モジュールは（店舗・操作者・操作キー）の助言ロックを一つの名前空間で、トランザクション範囲（PostgreSQL の `pg_advisory_xact_lock`）で取り、その後に受領を一度だけ照会する。ロックは確定または取消で解放され、セッション範囲のロックは使わない（接続プールへ返却した後も残り、後続の要求を止める）。取得の待ちには上限（`application.yml` の `app.receipt.lock-timeout-seconds`）があり、達したら処理を中止して何も確定しない。上限は取得の間だけ `lock_timeout` として掛け、取得後は既定へ戻すので、呼出側の業務行のロックの待ち方は変えない。業務行のロックはすべてその後に呼出側が取る。逐次・並行いずれの同一キー再送も直列化され、二つ目は受領を見て再送として解決する。一意制約は機械的な保証として残し、controller の捕捉と別トランザクションでの再送解決（ADR 0007 の形）は共通の補助として残す。
- **受領の記録と業務更新は同じトランザクションで確定し、同じトランザクションで取り消す。** 受領モジュールは呼出側の application service（トランザクション境界）の内側で動く協力者で、自分でトランザクションを開かない。業務が失敗すれば受領も残らず、受領だけが残って失敗した業務の再送を止めることも、業務だけが残って受領の無い再送が二重に実行されることも無い（業務監査と同じ規則）。
- **受領の照会は業務の検証より先に行い、再送は保持した内容をそのまま送る。** 同じキー・同じ内容の再送が業務拒否（400 / 404 / 409 / 422）を受けるのは受領が無いときだけ（受領が命中すれば検証を通らず現在の状態を返し、対象は物理削除されない）なので、それは初回が成立していないことを確定する。認可拒否（401 / 403）は受領の照会より前に起きるため初回について何も語らない。内容を変えて同じキーで送ることは再送ではない — その 409（内容不一致）は初回の成立を明告するもので（ADR 0007 の調整ダイアログの規則）、画面は結果不明の操作の内容を変えずに再送することでこの二つの 409 を混同しない。画面はこの一つの規則だけで結果不明の操作を扱い、同じ本人・同じ店舗の作用域でだけ再送する。この順序の保証と画面の規則は受領モジュールが記録する操作に限る。対象の行をそのまま受領とする同族（ポイント台帳・応募者添付・定期処理の実行要求）は各自の順序のままで、たとえばポイント調整は顧客と有効な会員紐づけの検証が台帳の照合より先にあり、初回成立の後に紐づけを解除してから再送すると業務拒否になる。これは ADR 0007 の範囲で本決定は変えず、これらの画面は共通の規則（hook）に載せない。行キーの同族では対象の行が受領そのものなので、行が消えれば受領も消える。応募者添付は保持期間の満了で匿名化され、添付の行と実体が削除されるため、その後の同じキーの再送は初回の新規アップロードとして扱われる。現行は終端状態の応募者への追加を拒み、匿名化は終端状態でしか起きないので、その再送は拒否されて二重に保存されることは無い。これを変えるかは添付の保持方針（ADR 0033 と応募者の匿名化）が決めることで、本決定の受領モジュールには関わらない。
- **wire 契約は変えない。** 各端点のキー項目名（`request_id` / `dedupe_key` / `idempotency_key`）、再送時の 200 / 201、応答の形は従来どおり。
- **ポイント台帳と定期処理の実行要求は対象の行を受領とする同族のまま置く。** ADR 0007 の「台帳に専用の鍵表を作らない」「再送は現在残高を返す」はそのまま有効で、本決定はそれと同じ口径を他の操作へ広げたものである。

## 検討した選択肢

- 各モジュールが自前の受領表を持ち、共通の実装へ adapter として渡す: 重複がコードから schema へ移るだけで、表の形は同じ四枚が残る。
- 受領に応答の写しを保存し、再送は写しを返す: 初回と再送の字節一致は得られるが、応答 DTO の改名が保存形式を黙って変え、再送の画面が現在の状態と食い違う「画面上の嘘」になる（ADR 0007 と同じ理由で不採用）。
- controller の捕捉と再送解決だけを共通化し、ロックは各モジュールに任せる: 口コミの「ロック前後の二重照会」のような補償が各所に残り、画面の規則を一つにできない。

## 帰結

- 受領の行は業務操作の数だけ増え、削除しない。保持期間を設けて行を消すと、期限後の再送が初回として扱われ同じ業務が二重に実行されるので、保持期間を導入する決定はその再送の扱い（期限切れのキーを拒む、または画面側でキーに有効期限を持たせる）と一緒に行う。それまでは無期限に保持する（業務監査と同じ扱い）。
- 口コミ・アンケートの再送応答に含める受領の情報（種別・対象・成立時の版）は受領の行から組み、「再送か否か」は今回の照会が命中したかで決め、対象の状態は現在のものを読み直す。再送の応答で受領の版と対象の現在の版が異なりうるのは従来どおりである。
- 受領モジュールの振る舞い（再送・内容不一致の 409・同一キーの並行で一度だけ成立）は実 PostgreSQL の試験で一度だけ検証し、各モジュールは受領を経由していることだけを検証する。画面側は一つの hook に対する表駆動の試験で「どの応答で忘れてよいか」を固定し、各画面は表示だけを検証する。
- 助言ロックの待ちの打ち切りは 503（`Retry-After` 付き）で返す。打ち切りは受領の照会より前に起き、保持者がこれから成立するかについて何も語らない。409 は画面が「初回は成立していない」として結果不明の操作を忘れる応答なので、保持者がその後に成立すると、利用者が新しいキーで送り直して二重に実行しうる。503 なら画面は操作とキーを保持したまま再送でき、保持者が成立していれば再送は受領に命中する。
- 候補として残る: 画面側の結果不明の表示を共通の部品にすること、ポイント調整・帰属訂正・添付・定期処理の画面を同じ hook に載せること、キー項目名の統一（wire 変更のため別の承認を要する）。
