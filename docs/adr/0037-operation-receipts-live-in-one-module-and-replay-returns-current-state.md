# 操作の受領は一つのモジュールに置き、再送は対象の現在の状態を返す

Status: Accepted

## 決定時の背景

応答を失った書き込みを利用者が安全にやり直せるようにする仕組み（GLOSSARY「操作の受領」）が、モジュールごとに別の形で実装されていた。広告費と報酬は専用の受領表に要求と応答の写しを置き、助言ロックで直列化する。口コミとアンケートは操作台帳に内容の指紋を置き、一意制約の違反を controller で捕まえて別トランザクションで再送を解決する。ポイント台帳は仕訳行そのものに冪等キーを持つ（ADR 0007）。応募者添付と定期処理の実行要求も対象の行にキーを持つ。

同じ不変条件が四つの形で書かれた結果、既に挙動が割れていた。再送に返す内容が写し（広告費）と現在の状態（口コミ・アンケート・定期処理）で異なり、報酬は初回と再送で直列化の経路が違う。受領表に応答の写しを置く設計は、応答 DTO の改名がそのまま保存形式の変更になる（媒体名を媒体 ID に替えた改修で既に起きた）。画面側も五つの画面が「結果不明の操作をいつ忘れてよいか」の表を各自に持ち、互いに矛盾していた。

## 決定

- **受領は一つのモジュールが所有する。** 業務監査（`audit`）と同じ形の独立モジュールが受領表を一つ持ち、公開パッケージを通じて各モジュールが利用する。受領の行は店舗・操作者・操作キーで一意で、操作名・内容の指紋・対象 ID・記録時刻を持つ。広告費・報酬の受領表と口コミ・アンケートの操作台帳はこの一表に置き換える。
- **再送は対象の現在の状態を返す。** 受領は応答の写しを持たない。再送を受けた呼出側は受領の対象 ID で現在の状態を読み直し、通常の応答と同じ形で返す。初回応答との字節一致は目的にしない。
- **指紋は内容の要約であって原文ではない。** 命令（sealed command など）が自身の同一性を決める項目から SHA-256 の指紋を作り、受領モジュールは指紋の文字列だけを受け取る。要求 DTO の JSON 全文は保存しない。
- **操作キーのロックをトランザクションの最初に取る。** 受領モジュールは（店舗・操作者・操作キー）の助言ロックを一つの名前空間で取り、その後に受領を一度だけ照会する。業務行のロックはすべてその後に呼出側が取る。逐次・並行いずれの同一キー再送も直列化され、二つ目は受領を見て再送として解決する。一意制約は機械的な保証として残し、controller の捕捉と別トランザクションでの再送解決（ADR 0007 の形）は共通の補助として残す。
- **受領の照会は業務の検証より先に行う。** このため再送に対する業務拒否（400 / 404 / 409 / 422）は初回が成立していないことを確定し、認可拒否（401 / 403）は初回について何も語らない。画面はこの一つの規則だけで結果不明の操作を扱い、同じ本人・同じ店舗の作用域でだけ再送する。
- **wire 契約は変えない。** 各端点のキー項目名（`request_id` / `dedupe_key` / `idempotency_key`）、再送時の 200 / 201、応答の形は従来どおり。
- **ポイント台帳と定期処理の実行要求は対象の行を受領とする同族のまま置く。** ADR 0007 の「台帳に専用の鍵表を作らない」「再送は現在残高を返す」はそのまま有効で、本決定はそれと同じ口径を他の操作へ広げたものである。

## 検討した選択肢

- 各モジュールが自前の受領表を持ち、共通の実装へ adapter として渡す: 重複がコードから schema へ移るだけで、表の形は同じ四枚が残る。
- 受領に応答の写しを保存し、再送は写しを返す: 初回と再送の字節一致は得られるが、応答 DTO の改名が保存形式を黙って変え、再送の画面が現在の状態と食い違う「画面上の嘘」になる（ADR 0007 と同じ理由で不採用）。
- controller の捕捉と再送解決だけを共通化し、ロックは各モジュールに任せる: 口コミの「ロック前後の二重照会」のような補償が各所に残り、画面の規則を一つにできない。

## 帰結

- 受領の行は業務操作の数だけ増え、保持期間は未定（業務監査と同じ扱い）。
- 口コミ・アンケートの再送応答に含める受領の情報（種別・対象・確定版・再送か否か）は、受領の行と対象の現在の状態から組む。
- 受領モジュールの振る舞い（再送・内容不一致の 409・同一キーの並行で一度だけ成立）は実 PostgreSQL の試験で一度だけ検証し、各モジュールは受領を経由していることだけを検証する。画面側は一つの hook に対する表駆動の試験で「どの応答で忘れてよいか」を固定し、各画面は表示だけを検証する。
- 候補として残る: 画面側の結果不明の表示を共通の部品にすること、ポイント調整・帰属訂正・添付・定期処理の画面を同じ hook に載せること、キー項目名の統一（wire 変更のため別の承認を要する）。
