# アクセストークンはタブのメモリに、リフレッシュトークンは HttpOnly cookie に置く

Status: Proposed

フロントはアクセストークンを JS から読める cookie に置かず、タブのメモリ（ページの生存期間）だけに持つ。継続ログインはバックエンドが HttpOnly cookie で発行するリフレッシュトークンが担い、タブは開いたときと 401 を受けたときに `POST /auth/refresh` でアクセストークンを取り直す。

## 決定時の背景

フロントの身分・権限の出所を `GET /me`（layout の生存期間で保持）へ移した（ADR 0035）一方、トークンは全タブ共有で JS から読める `token` cookie に残っていた。別タブで別アカウントにログインすると、旧タブの要求は新しいアカウントのトークンで送られ、画面は旧アカウントのまま残る。原因は、同期していなければならない二つ（画面が示す本人と、要求が名乗る本人）が異なる生存期間の保存場所にあることだった。

## 決定

- **アクセストークンはタブのメモリにだけ置く。** `shared/api` のモジュール変数にトークンとその利用者 ID を一緒に保持し、cookie・localStorage・sessionStorage には書かない。有効期間は 15 分（`APP_JWT_EXPIRATION_MS` の既定値）。タブごとに自分の本人のトークンを持つため、画面の本人と要求の本人が同じ生存期間に収まる。
- **リフレッシュトークンは署名付き JWT で、資格情報の版を載せる。** claim は `typ=refresh`・`userId`・`credentialVersion`。有効期間は 14 日（`APP_JWT_REFRESH_EXPIRATION_MS`）。失効は既存の機構に乗る: 版の増分（パスワード変更・停止・実効権限の変更、ADR 0022）で失効し、ログアウトは `blacklist:tokens:` へ登録する。新しいテーブルは作らない。
- **リフレッシュトークンの期限はスライディング方式で延長する。** `/auth/refresh` が成功するたびに新しいリフレッシュトークンを発行して cookie を差し替え、期限をその時点から 14 日に取り直す。旧いトークンは失効させず、自身の期限まで有効のままにする。旧トークンを使えなくするローテーションではないので、盗用の検知は持たず、複数タブが同時にリフレッシュしても衝突しない。盗まれたトークンの失効は版の増分とログアウトのブラックリストが担う。
- **リフレッシュで発行するアクセストークンは DB から組み立て直す。** 権限・利用者種別はログインと同じ単一の発行点で DB から読み、旧いトークンの claim を写さない。
- **不変量: `GET /me` の権限または利用者種別を変える操作は、必ず資格情報の版を増分する。** フロントはリフレッシュでトークンだけを取り替え、`GET /me` を取り直さない。この前提が崩れると、画面の権限と要求のトークンの権限が食い違ったまま残る。
- **トークンの種別を相互に拒否する。** アクセストークンは `typ=access` を載せ、Bearer の検証は `typ=access` 以外（欠落を含む）を拒否する。`/auth/refresh` は `typ=refresh` 以外を拒否する。署名鍵は共有するため、種別の照合が無いとリフレッシュトークンが Bearer として通る。
- **cookie 属性**: 名前 `refresh_token`、`HttpOnly`、`SameSite=Strict`、`Path=/api/auth`、ホスト限定（`Domain` を付けない）、`Max-Age` はトークンの残存期間。`Secure` は設定で切り替え、release で有効、http の開発・e2e 環境で無効にする。
- **発行はトークンを返す三つの端点**（`/auth/login`、`/auth/line/login` の登録済み応答、`/auth/line/register`）と `/auth/refresh` で行う。応答本文は従来どおりアクセストークンを返し、`user_id` と `refresh_expires_at` を加える。curl や e2e の助手は本文のトークンを Bearer で使い続けられる。
- **リフレッシュの失敗は原因を区別して返す。** 401 には応答ヘッダ `X-Auth-Failure` で原因を付ける: `credential_changed`（版の不一致）、`missing`（cookie が無い）、`expired`（期限切れ）、`invalid`（署名・種別の不正、ブラックリスト済み）。`credential_changed` のとき、フロントは「権限やパスワードが変更されました。もう一度ログインしてください」とボタンを出し、利用者が押してからログインへ移る（自動では遷移しない）。それ以外の 401 は従来どおりログインへ差し戻す。
- **タブ間の本人の照合は `/auth/refresh` だけで行う。** 共有されるのはリフレッシュ cookie だけなので、照合する地点もここだけでよい。タブは自分の利用者 ID を `X-Session-User-Id` で送り、cookie の `userId` と違えば 409（`{ "error": … }`）を返し、cookie はそのまま残す。フロントは再読込を促すダイアログを出し（入力中の内容を黙って捨てないため自動では再読込しない）、再読込後は cookie の本人として始まる。ヘッダが無ければ照合しない（タブを開いた直後の取得）。
- **ログアウトは同じブラウザの他のタブへ知らせる。** `/auth/logout` はアクセストークン（従来どおり）とリフレッシュトークンをブラックリストへ登録し、`Set-Cookie` で cookie を失効させる。フロントは `BroadcastChannel` で他のタブへ通知し、受け取ったタブはメモリのトークンを消してログインへ移る。送信元のタブには自分の通知が届かないため、自分でも消す。通知は体験の改善であって安全の保証ではない: 届かなかったタブも手元のアクセストークンの期限（最大 15 分）の後はリフレッシュが失敗して退出する。
- **CSRF はバックエンドの `CookieCsrfTokenRepository` を撤去する。** 認証済みの要求は Bearer だけで、cookie では認証しない。cookie を読む端点（`/auth/refresh`・`/auth/logout`）は `SameSite=Strict` に加えて `X-Requested-With: XMLHttpRequest` を必須にし（無ければ 403）、CORS を開いていないので別オリジンからはプリフライトで止まる。ログイン系の端点は JSON 本文を要求するため、フォームによる偽装送信は 415 で止まる。
- **招待の受諾（既存の利用者）は認証と受諾を一回の匿名要求で行う。** 本文に資格情報と招待トークンを受け、トークンも cookie も発行しない。訪問者がすでに持っている別のセッションには触れない。

## ADR 0035 との関係

変わるのは「トークンを JS 可読の cookie に置く」前提だけで、`GET /me` を layout の生存期間で保持すること、フロントが JWT を解読しないこと、画面遷移の守衛を置かないことは変わらない。全域の 401 経路は「一度だけリフレッシュして再送し、それでも 401 ならログインへ差し戻す」に変わる。

## 検討した選択肢

- BFF（Next のルートハンドラが代理）とサーバー側のトークン保存: バックエンドを公開せずに済むが、セッション cookie は全タブで共有されるため、タブ間の食い違いは別途照合が要る。代理層がアップロードのストリーミング転送・`X-Forwarded-For`・CSRF を新たに抱える。アクセストークンをタブのメモリに置けば食い違いそのものが起きないので不採用。
- 暗号化 cookie（iron-session / jose）にトークンを入れる: 秘密鍵の管理が増え、権限の全集合を持つ JWT は暗号化後に約 3KB で 4KB 上限に近い。JWT の内容は保持者が読んでよいもので、暗号化で守るものが無い。
- 絶対期限（延長しない）: 実装は最小だが、使い続けている利用者も 14 日ごとにログインし直すことになる。
- ローテーション（不透明トークンを DB に保存し、使うたびに旧いものを失効させる）: 盗用の検知はできるが、複数タブが同時にリフレッシュすると同じ旧トークンを二度出して盗用と誤判定する。猶予期間かタブ間ロックが要る。HttpOnly で XSS から読めない以上、利点は小さい。スライディング延長は旧トークンを失効させないので、この衝突が起きない。
- `token` cookie を HttpOnly にするだけ: 全タブ共有のままで、根本原因が残る。

## 帰結

- 画面を開くたびに `/auth/refresh` が 1 回走り、続いて `GET /me` が走る。アクセストークンの期限切れでは 401 → リフレッシュ → 再送の往復が 1 回増える。
- 14 日以内に一度でも使えばログインが続く。発行済みのリフレッシュトークンは延長後もそれぞれの期限まで有効なので、盗まれたトークンを止めるのは版の増分かログアウトだけである。
- 別タブで別アカウントにログインしても、旧タブはアクセストークンの期限（最大 15 分）まで旧アカウントとして正しく動き、次のリフレッシュで 409 を受けて再読込を促す。
- 権限やパスワードの変更でアクセストークンが即時に失効するのは従来どおりである（版の照合は毎要求で行う）。続くリフレッシュも `credential_changed` で失敗し、再ログインを求める。
- XSS はページが開いている間、メモリ上のアクセストークンを使えるが、リフレッシュトークンは持ち出せない。
- 資格情報の版の Redis キャッシュは TTL がアクセストークンの有効期間（15 分）のままで、14 日のリフレッシュトークンに対しては旧い版を DB を読まずに拒否する近道がほぼ効かない。照合は毎回 DB で行うので正しさは変わらない。
- `session-kind` cookie（ルート画面の振り分けの手がかり）の期限は `refresh_expires_at` に揃え、リフレッシュのたびに延ばす。
