# 予約申請は受注と別の記録であり、すべての受注は確定で出生する

Status: Accepted

## Context

会員ポータルの予約申請は、これまで受注（Order）の `CREATED` 状態として同一行に起きていた（#334 の「早期に
受注作成フローへ合流」形態）。店舗の確定で同じ行が `CONFIRMED` になるため、申請と受注の区別が無く、
申請時の原文（希望内容）は店舗の編集・確定でそのまま上書きされて残らない。#380（受注の拡張）の要件 1 は
「申請と確定受注が区別され、確定後も対応が照会できる」ことを求めており、この形態はそれと正面衝突する。

業界調査（#747）では予約域の標準は同一レコードの状態遷移だが、本システムの Order は売上・給与・ポイントの
根拠となる財務集約である。商務域には未確定の意向を別レコードで受け、成立時に変換リンクで正式な記録を生む
型（Draft Order → Order）があり、こちらが適合する（#748）。さらにゲスト（未ログイン）申請の入口（#749）を
控えており、未検証の投稿が財務集約のテーブルへ直接行を作る構造は受け皿として不適切である。

シフト系列には既に「申請行は不変のまま残し、承認が生んだ正式な行の id を申請行へ回写する」先例がある
（ShiftRequest.shift_id、#719）。また ADR 0013 は終端状態（COMPLETED / CANCELLED）の凍結を `isTerminal`
一本で守っており、申請のライフサイクル（謝絶・取り下げ）が受注の状態機械に絡まっていることが、その語義を
濁す唯一の残余だった。

## Decision

- **予約申請は独立した付随記録 OrderApplication（`t_order_applications`）として持つ**。会員・ゲスト共用の
  受け皿で、店舗への帰属は他の店舗行と同じく `store_id`（StoreScopedEntity）が担う。
- **状態は `PENDING` → `CONFIRMED` / `DECLINED` / `WITHDRAWN` の四値**。終端は三つすべてで、終端に入った
  申請行は以後動かない — 申請原文（希望内容）は確定内容との対照先として不変のまま残る。
- **失効は状態に持たず導出する**。希望日を過ぎた `PENDING` は失効として扱い（表示と確定・謝絶の拒否）、
  バッチは置かない。先例は欠勤導出（#720「存在即出勤・欠勤は導出」）。
- **確定は申請内容を予填した受注の作成操作**である。店舗が補完・調整（指名・時刻・人数など）した確定内容で
  Order を **CONFIRMED で生成**し、申請行へ `order_id` を回写する（シフトの回写方式に倣う）。生成された
  受注は申請者のスナップショット（会員参照・会員コード・名乗り）を写しとして持つ。
- **謝絶は理由必須**で、実行者と時刻を記録に残す（取消 ADR 0013 の先例）。理由は分類軸ではないため
  enum 化しない。
- **`OrderStatus.CREATED` は退場する**。これにより**すべての Order が出生即 CONFIRMED** となり、店舗直接
  受注（#679 既決）と出生が揃う。受注の状態機械は `CONFIRMED → COMPLETED / CANCELLED` だけになり、
  ADR 0013 の終端語義に申請ライフサイクルが絡まなくなる。
- **受付経路 `MEMBER_WEB` / `GUEST_WEB` は申請確定由来の受注だけが名乗る**。入口ごとに値が分かれ、
  会員ポータル由来が `MEMBER_WEB`、公開店面のゲスト申請由来が `GUEST_WEB` になる。店舗・HQ の作成経路が
  Web 申請の経路を拒否する既決（CONTEXT.md）は変えない。

## Consequences

- 会員の申請は `t_orders` に行を作らない。店舗の受付箱・会員マイページの申請一覧・取り下げは申請テーブル
  起点の読み口（`/store/order-applications`・`/platform/me/order-applications`）へ移る。
- 申請と確定受注の対応は `order_id` の回写で恒久的に照会できる。確定時の調整（人数変更など）は受注側にだけ
  現れ、申請原文と突き合わせられる。
- 確定前の申請内容を店舗が書き換える口（旧 `PUT /store/orders/{id}/reservation-request`）は持たない。
  調整は確定操作の一部として行う — 原文を直せる口を残すと「不変のまま対照できる」が成り立たない。
- 顧客台帳との紐づけ（確定時自動整備、ADR 0008）は引き続き確定の瞬間に「今の関連」だけを見て行う。
  申請は顧客参照を持たない。
- 失効した `PENDING` は行として残り続ける（本人の取り下げは可能）。件数が問題になったら掃除を検討するが、
  状態を持たない以上、導出の判定が変わることはない。
- ゲスト申請の入口（#757）はこの受け皿に列を足すだけで済み、`t_orders` の契約に触れない。
