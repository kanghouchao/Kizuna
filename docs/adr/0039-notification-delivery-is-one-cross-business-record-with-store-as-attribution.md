# 通知の送信正本は業務を跨いで一つにし、店舗を帰属属性・起点を多態参照にする

Status: Accepted

## 決定時の背景

業務連絡の送信正本は、受注・ゲスト申請を起点とする店舗の業務メールのために作られた。起点は型付きの外部キー列二本（`order_id` / `application_id`）、チャネルと用途は定数、店舗は StoreScope の隔離軸で、GLOSSARY は販促・SMS・LINE への流用を避ける設計として記していた。最初の業務に正本の形を合わせた結果、次に来る業務はどれも載らない。ポイント期限前案内と有料会員の案内はいずれも会員宛で、会員はグループ級の集約であり起点は受注ではない。ポイントは会員に帰属して店舗を跨ぐ（ADR 0006）ので、店舗を隔離軸とする正本には起票先の店舗が無い。

期限前案内の要件は旧システムに由来しない。旧システムの挙動は要件の根拠としない裁定（2026-10-20）のもとで、会員宛の通知が今後の主な消費者になるという判断から本決定で初めて置いた。

## 決定

- **正本は一つ。** 業務ごとの送信表を作らない。送信状態・再送・試行履歴・結果不明（UNKNOWN）の判定は正本が一元管理し、業務側は起点・用途・チャネル・内容・予約日時・重複排除キーを渡すだけで、以後の状態を持たない。
- **店舗は帰属属性。** 帰属店舗 `attributed_store_id` は会員宛で null になり、StoreScope の隔離軸ではない（業務監査・定期処理の実行追跡と同じ扱い）。グループ級の行の照会・操作は通知の権限に加えて ALL_STORES を要する。送信の定期処理はグループ全体の処理として全店舗の到来分を扱う。
- **起点は多態参照。** （起点種別, 起点 ID）の二列で持ち、外部キーを張らない。起点種別は宛先を提供する集約（ORDER / APPLICATION / MEMBER）であって業務の種類ではない。種別ごとに一つの解決器が送信直前に連絡先と用途別の連絡可否を返し、起点が無ければ SOURCE_UNAVAILABLE、連絡先が無ければ NO_CONTACT として BLOCKED に落とす。通知の内容と起点は不変で、起点が消えても通知は残るので、外部キーが守っていた整合は元から無かった。
- **用途とチャネルは正本の次元。** 用途（BUSINESS / MARKETING）ごとに連絡可否を強制し、業務の許可から販促の許可を推定しない（ADR 0028 の原則をそのまま適用する）。チャネルは作成時に明示指定し、基盤は自動選択しない。チャネルの追加は enum の値・チャネル実装・解決器の対応だけで、正本の表は変えない。そのため DB の check は用途・チャネルの値を列挙せず、`notificationdelivery` は具体チャネル実装に依存しない（ArchUnit で固定する）。
- **販促の入口は閉じたまま。** HTTP の作成口は BUSINESS だけを受け、販促を渡すコードの消費者も置かない。解決器の販促判定（顧客連絡先の販促可否、会員の通知設定の販促）は実装し試験する — 入口を開く日に基盤側の不変条件が揃っているようにするため。
- **会員宛の宛先と同意。** 宛先は会員のログイン用メールアドレス。同意は会員本人だけが持つ会員の通知設定で、職員は閲覧も代理変更もしない。通知設定は本人の明示の選択だけを保持し、明示の選択が常に優先する。明示の選択が無い業務の既定はメールアドレスの検証状態（ADR 0040）から導き、検証済みなら許可・未検証なら未確認とする。販促の既定は検証状態に依らず未確認。未確認では送らない。本決定の時点では登録時のメールアドレスは検証されない（メール・パスワード / LINE のどちらの経路も本人の入力をそのまま保存する）ので、検証が入るまで会員宛の既定は実質すべて未確認である。店舗の顧客連絡先の連絡可否とは独立で、互いに推定も同期もしない。

## 検討した選択肢

- 会員宛の送信正本を別に置く: 状態機械・再送・UNKNOWN の判定が二重になり、有料会員の案内が来たとき三つ目を選ぶことになる。不採用。
- 起点ごとに型付き外部キー列を増やす: 業務が一つ増えるたび表と check が変わり、「業務の追加が正本の構造を変えない」が成り立たない。不採用。
- チャネルを基盤が自動選択する: 優先順位と代替の規則が要るが、チャネルは一つで規則を検証する相手が無い。作成時の明示指定にした。

## 帰結

- 期限前案内は通知設定で業務連絡を許可した会員にだけ届く。登録時のメールアドレス検証を導入すれば、検証済みの宛先について業務の既定を許可に改められるが、それは別の決定である — ADR 0040（メールアドレスの検証）がその決定で、検証済みの宛先では業務の既定を許可にし、検証メールは送信正本を通さない。

- 受注・ゲスト申請の片（最初の実装）は起点列・check・解決器の接続を作り直す。既存端点の項目名と形（`source_type` / `source_id` は wire では既にこの形）は維持し、値域の拡張（MEMBER、グループ級の行）と新しい端点（UNKNOWN の判定、会員の通知設定、グループ級の一覧）は API 契約の承認を経て追加する。
- 会員は登録経路（メール・パスワード / LINE）を問わずログイン用メールアドレスを必ず持つので、会員宛の EMAIL は NO_CONTACT にならない。NO_CONTACT は解決器の一般の結果として残す。
- グループ級の通知はサイドバー「グループ」コンテキストの通知一覧に出る。店舗の一覧は従来どおり自店の行だけ。
- 会員ポータルの通知センター（本人が受け取った通知を見る画面）は本決定の範囲外で、別の実装 issue に残す。
