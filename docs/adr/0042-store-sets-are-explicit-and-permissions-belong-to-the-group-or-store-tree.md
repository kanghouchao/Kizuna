# 店舗集合は明示した店舗だけで、権限はグループか店舗のどちらか一方の木に属する

Status: Accepted

## 決定時の背景

授権の店舗軸は ALL_STORES / SPECIFIC_STORES の二択で、ALL_STORES は「後から作られた店舗も含む」暗黙の全店だった。審計・定期処理・グループ級の通知は ALL_STORES を条件にし、店舗の作成・編集・削除は店舗集合を見ていなかった。権限の側では、単店の端点が店舗集合を跨ぐ照会の権限（`ORDER_SET_VIEW` など）も受け付け、一つの権限がメニューとダッシュボードの複数の場所を同時に開いていた。管理画面では、グループ級の権限を一つでも持てばグループの文脈が、店舗集合があれば店舗級の権限が無くても全店舗のボタンが出て、利用者の役割と画面が対応しなかった。

## 決定

- **店舗集合は明示した店舗の集合だけ。** ALL_STORES とその判定を撤去する。集合は空でもよい。画面の「全選択」はその時点の店舗を選ぶ操作で、後から作られた店舗は含まない。店舗を作成した者には、その店舗を自動で加える。それ以外の者（サービス ID を含む）へは誰かが明示で加える。
- **権限はグループの木か店舗の木のどちらか一方に属し、一つの権限は一つの場所だけを開く。** 両方で使われていた権限は分割する。単店の端点は店舗の木の権限だけを、店舗集合を跨ぐ端点はグループの木の権限だけを受け付ける。ダッシュボードの区画も区画ごとに権限を持つ。ロールは権限の束のまま、店舗集合は User に属したままで、店舗をロールに結び付けない。
- **ダッシュボードの区画は専用の端点を持ち、その端点は区画の権限だけで守る。** 区画の権限は一覧の権限を前提とせず、集計の数字だけを開く。数字から一覧への導線は一覧の権限で出し分ける。売上の区画は今は運営集計と同じ数字を返すが、意味も権限も別の能力として別の端点に置く。
- **管理画面は三階層。** 一階層目はグループと各店舗（左端のレール）、二階層目は区分見出し、三階層目は機能。メニューの木もこの形で持ち、グループと店舗それぞれにダッシュボードがある。どの文脈かは URL が決め、店舗の文脈は URL に店舗 id を持つ（`/store/{storeId}/...`）。`X-Store-ID` は URL の店舗 id から付け、現在店舗の cookie は持たない。何も選んでいなければ一階層目の先頭（グループがあればグループ、無ければ作成日の新しい店舗）へ着地する。未ログインで開いた画面は、従業員・キャスト・会員とも `/auth/login?next=<パス>` で預けてログイン後に戻す。`next` は本人種別ごとの本站の相対パスだけを受け付け、伝票トークンのような断片はログイン画面の URL の断片で持ち越す（断片はサーバへ送られない）。会員専用の戻り先 cookie は撤去する。
- **ALL_STORES に頼っていた照会は権限と店舗集合で絞る。** 審計は集合内の店舗の行と、店舗を持たない行（グループ級の操作）と、既に存在しない店舗の行を返す。店舗の管理は集合内の店舗だけを扱う。定期処理は実行するサービス ID の店舗集合で店舗級のデータを絞り、店舗を持たないグループ級のデータ（会員のポイント・会員宛の通知）は絞らない。従業員の一覧は集合が交わる者と集合が空の者を返し、編集は委譲の二条（権限の部分集合・店舗集合の部分集合）で判定する。
- 特典規則の「適用店舗: 全店舗」は発火側の絞り込みで授権ではないため残し、授権の型とは別の型にする。

## 検討した選択肢

- ALL_STORES を残し、全選択と並べる: 「後から作られた店舗も見える者」が残り、店舗の作成者以外に新店舗が届く経路が二つになる。統括は通常一人で、作成者の自動付与で足りるため不採用。
- 店舗集合をロールに持たせる（権限の木で店舗も選ぶ）: 店長ロールを店ごとに複製することになり、権限を一つ変えるたびに全複製を直す。不採用。
- 一つの権限で複数の場所を開いたままにする: 権限の木で一項目を外したときに何が消えるかが読めず、単店と店舗集合の境も権限から読めなくなる。不採用。
- ダッシュボードの区画を既存の一覧・集計の端点で描き、区画の権限は表示の切り替えだけにする: 区画の権限を持ち一覧の権限を持たない者には区画が描けず、一覧の権限を持つ者には区画を隠しても同じ数字が一覧で見える。区画の権限が何も守らないため不採用。
- 会員の戻り先 cookie を残し、従業員だけ `?next=` にする: 戻り先の仕組みと開放リダイレクトの白名単が二つになる。断片をクエリに載せないことは、ログイン画面自身の断片で持ち越せば `?next=` でも守れる。不採用。
- 現在店舗を cookie に置いたまま、URL では文脈だけを表す: 共有されたリンクを別の現在店舗で開くと別店舗の画面になる。不採用。
- 定期処理を店舗集合で絞らない: サービス ID の店舗集合が意味を持たなくなる。新店舗を加え忘れる危険は、どのサービス ID の集合にも入っていない店舗を実行追跡の画面に示して補う。

## 帰結

- 新店舗は作成者以外の誰にも見えない。統括が複数いる運用では、各自が全選択をやり直す。
- 店舗集合が交わらない者同士は互いの従業員を編集できない。集合が {1,3} の従業員は、{1,2} の管理者からは見えても編集できない。
- 審計で店舗を持たない行は、店舗集合に関わらず閲覧権限を持つ全員に見える。閲覧権限をグループの木に置き、既定で統括にだけ授与することで、従業員の授権変更が店舗の担当者に見えないようにする。
- 売上の数字を読む端点が運営集計とダッシュボードの二つになる。数え方は一つの読み取りに集め、二つの端点が別の数え方を持たないようにする。
- 管理画面の URL・メニューの種子・ロール編集画面・e2e の共通手順（店舗を省くと ALL_STORES を付けていた従業員の作成）はすべて書き換えになる。
- ADR 0031 の「ALL_STORES なら店舗条件を付けない」、ADR 0039 の「グループ級の行は ALL_STORES を要する」、ADR 0035 の「直打ちの 403 は画面に出す」（従業員の管理画面では、権限の無い画面は既定の着地へ戻して警告を出す）を本 ADR で置き換える。
