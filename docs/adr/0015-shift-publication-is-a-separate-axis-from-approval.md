# シフトの公開可否は承認と別の軸であり、店外露出だけを絞る

Status: Accepted

## Context

現行実装では承認＝公開である: 店舗が承認（CONFIRMED 化）したシフトは公式サイト出勤表
（`GET /store/shifts/public`）にそのまま載る。#379 要件 2 は、承認されていても店外へ出したくないシフト
（キャスト個人の事情・内密の出勤）のために、公開可否を承認と独立の軸として要求する。

業界（#721）では draft → published の区別が標準で、publish の語義は「従業員（本人）に見えるようになる」
可視性の境界であり、承認とも通知とも別ダイヤルである。本システムでは本人可視は承認そのものが担うため、
公開可否が引くべき境界は店外 — 匿名訪問者と会員 — への露出である。

動かせない既決として、受注確定の内部検証（hasConfirmedShift）は当日の確定シフトを要求し、この検証が
公開可否に巻き込まれてはならない（#717）。

## Decision

- **公開可否 = 「店外（匿名訪問者 + 会員）へこのシフトを露出してよいか」の行単位フラグ**（`t_shifts`、
  NOT NULL）。店外露出の十分条件は **CONFIRMED ∧ 公開可** の一つの述語であり、公式サイト出勤表と
  会員ポータルの指名候補の**両方**がこれで絞る。片面だけ絞ると軸が形骸化し、開放登録の会員経由の
  列挙経路が残る。
- **既定は承認時公開可**。この業態では出勤表が集客手段であり、公開が常態・隠蔽が例外。既定 = 非公開は
  毎日の明示公開を強い、漏れ＝当日出勤表が空白という運用事故源になる。
- **負向不変量**: 受注確定の内部検証（hasConfirmedShift）と店舗側管理画面は公開可否を見ない。公開可否は
  店外露出のフィルタであって、状態機械の一部ではない。
- **TENTATIVE は公開可否の値に関わらず店外へ出ない**（CONFIRMED の関門を通らない限り出ない）。フラグ列
  は全シフト行に通常列として持たせ、「TENTATIVE では null」のような追加不変量は設けない。
- **権限は SHIFT_MANAGE のまま**。切替は承認と同じ人の同じ日常業務であり、第二の具体的場面が無いままの
  権限分割は RBAC の膨張になる。切替操作の専用留痕も持たない（updated_at のみ）。
- **変更申請の承認でシフトが更新されても、公開可否の設定は独立に保持される**（#379 既決）。

## Consequences

- 確定済みだが非公開のシフトへ、会員がオンラインで指名予約することはできなくなる。これは望む挙動である
  （店舗が公開していない＝集客していない。電話経路と店内での受注確定は生きている）。
- 承認が「将来分の即時曝露」になることはない: 公開読み口が当日分しか返さないため、曝露時点は読み口側で
  当日に留まる。
- 公開切替の実行者・時刻は追跡されない。必要になれば列を足す。
- 一括公開/非公開は UI 上の一括操作にすぎず、データは逐行更新する。UI の形は #722 が確定する。
