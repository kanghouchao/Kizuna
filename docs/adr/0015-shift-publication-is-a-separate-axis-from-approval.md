# シフトの公開可否は承認と別の軸であり、店外露出だけを絞る

Status: Accepted

## Context

現行実装では承認＝公開である: 店舗が承認（CONFIRMED 化）したシフトは公式サイト出勤表
（`GET /store/shifts/public`）にそのまま載る。#379 要件 2 は、承認されていても店外へ出したくないシフト
（キャスト個人の事情・内密の出勤）のために、公開可否を承認と独立の軸として要求する。

業界（#721）では draft → published の区別が標準で、publish の語義は「従業員（本人）に見えるようになる」
可視性の境界であり、承認とも通知とも別ダイヤルである。本システムでは本人可視は承認そのものが担うため、
公開可否が引くべき境界は店外 — 匿名訪問者と会員 — への露出である。

動かせない既決として、受注確定の内部検証（hasConfirmedShift）は当日の確定シフトを要求し、この検証が
公開可否に巻き込まれてはならない（#717）。

## Decision

- **公開可否 = 「店外（匿名訪問者 + 会員）へこのシフトを露出してよいか」の行単位フラグ**（`t_shifts`、
  NOT NULL）。シフト側の露出関門は **CONFIRMED ∧ 公開可** の一つの述語であり、公式サイト出勤表と
  会員ポータルの指名候補の**両方**がこれで絞る。キャスト在籍（ACTIVE）などシフト外の既存条件はそのまま
  重なる — 本 ADR が定めるのはシフト側の軸だけで、この述語単独の十分条件化ではない。片面だけ絞ると
  軸が形骸化し、開放登録の会員経由の列挙経路が残る。
- **会員経由の指名の書き込み検証は、候補の読み口と同じ述語を共有する**。候補から隠すだけでは cast_id の
  直送を防げない（CONTEXT.md「指名 / 指名候補」の既決規則の適用）。公開可否を見ないのは店舗側の
  受注確定の内部検証（hasConfirmedShift）であって、会員面の検証ではない。検証の粒度は候補と同じ
  （キャスト・営業日）— 当日に公開可の確定シフトが 1 本でもあればそのキャストは当日の候補であり、
  指名できる。公開可否が守るのは店外への**可視性**であり、同日に非公開シフトが併存しても、その時間帯を
  会員の到着時刻から仕切る機構ではない（指名は従来から日粒度で、時間帯の照合は存在しない）。
- **既定は承認時公開可**。この業態では出勤表が集客手段であり、公開が常態・隠蔽が例外。既定 = 非公開は
  毎日の明示公開を強い、漏れ＝当日出勤表が空白という運用事故源になる。
- **非公開での出生を要する場合、承認・直接作成は公開可否を同一トランザクションで指定できる**。行が
  公開状態で生まれてから隠すまでの露出窓を作らない（内密の出勤という本軸の動機事例は、承認の瞬間から
  非公開でなければ守れない — 会員ポータルは将来分も即時に返すため窓は実害になる）。指定が無ければ
  既定の公開可で生まれる。
- **負向不変量**: 受注確定の内部検証（hasConfirmedShift）と店舗側管理画面は公開可否を見ない。公開可否は
  店外露出のフィルタであって、状態機械の一部ではない。
- **TENTATIVE は公開可否の値に関わらず店外へ出ない**（CONFIRMED の関門を通らない限り出ない）。フラグ列
  は全シフト行に通常列として持たせ、「TENTATIVE では null」のような追加不変量は設けない。
- **権限は SHIFT_MANAGE のまま**。切替は承認と同じ人の同じ日常業務であり、第二の具体的場面が無いままの
  権限分割は RBAC の膨張になる。切替操作の専用留痕も持たない（シフト行の汎用の最終更新者・更新時刻のみ）。
- **変更申請の承認でシフトが更新されても、公開可否の設定は独立に保持される**（#379 既決）。

## Consequences

- 確定済みだが非公開のシフトへ、会員がオンラインで指名予約することはできなくなる。これは望む挙動である
  （店舗が公開していない＝集客していない。電話経路と店内での受注確定は生きている）。
- 匿名の公式サイト出勤表の「当日」は、営業日（プラットフォーム統一の日付変更時刻 — ADR 0014）で判定
  する。現行の暦日 `LocalDate.now` のままでは、日付変更時刻より前の深夜帯に前営業日の出勤が消えて
  翌営業日分が早出しする — 営業日の導入と同時に公開読み口も切り替える（#379 の再計画）。
- 匿名の公式サイト出勤表は当日分しか返さないため、承認が匿名面での将来分の即時曝露になることはない。
  会員ポータルの指名候補は指定日（最長 90 日先）の候補を返す既存仕様のままなので、将来分も
  CONFIRMED ∧ 公開可 になった時点で会員には見える — これは意図した挙動で、隠したい将来分は公開可否を
  落とすことで対応する。
- 公開切替に専用の追跡は無く、シフト行が汎用に持つ最終更新者・更新時刻（`updated_by` / `updated_at`）へ
  相乗りする。誰がいつ切り替えたかを独立して辿る必要が出たら、そのときに専用の列か表を足す。
- 一括公開/非公開は UI 上の一括操作にすぎず、データは逐行更新する。UI の形は #722 が確定する。
