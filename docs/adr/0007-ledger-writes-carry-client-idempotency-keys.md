# 台帳への人手書き込みはクライアント生成の冪等キーで再送を機械的に遮断する

Status: Accepted

## Context

ポイント台帳（`t_point_entries`）は追加型で、残高は行の合計としてのみ求まる。したがって「同じ書き込みが
二度届く」ことは上書きではなく残高の二重変動である。サーバ側で commit が成立したのに応答が失われた場合、
画面は失敗と表示して再送信を受け付けるため、利用者の正常な回復操作（もう一度押す）がそのまま二重記帳になる。

台帳の書き込み口のうち、受注完了に伴う付与・利用は「CONFIRMED のみ完了できる」状態遷移が天然の再送防御に
なっている。手動ポイント調整（`POST /store/customers/{id}/point-adjustments`）にはそのような前提状態が
存在せず、要求そのものに操作の同一性を示す情報が無い。内容の一致だけでは「同一操作の再送」と「同内容の
正当な二回目」を区別できないため、操作の同一性はクライアントにしか分からない。

## Decision

操作の同一性は**クライアント生成の冪等キー**で表明させ、台帳側の**一意制約**で機械的に強制する。

- キーは要求ボディの必須項目 `idempotency_key`（最大 64 文字の不透明な文字列。クライアントは
  `crypto.randomUUID()` を用い、ダイアログを開くたびに生成して失敗再送・内容変更では変えない）。
  ヘッダーではなくボディに載せるのは、第一者 API であり、DTO の Bean Validation と wire 契約テストの
  管轄へ自然に入るため。
- 保存先は `t_point_entries` の可空列 `idempotency_key` と一意制約 `uq_t_point_entries_idempotency_key`。
  PostgreSQL の UNIQUE は NULL 同士を別値と扱うため、キーを持たない仕訳種別と部分インデックスなしで共存
  する。応答スナップショットを持たないため専用の鍵表は作らない。
- 再送（キー命中・内容一致）は記帳せず**現在残高**を返す。冪等が守るのは台帳の単記であって応答のバイト
  一致ではない。初回応答の残高を再現すると、その間の他経路の記帳を隠した「画面上の嘘」になる。
- キー命中・**内容不一致**は 409 で「初回の調整は既に成立しています」と明告する。比較は既存行の
  `amount / reason / expires_on / member_id / originating_store_id` との逐項比較（行が既に全部持って
  いるため新規列は不要）。内容変更時にクライアントがキーを振り直す設計は採らない — 初回成立を知らない
  利用者の「修正のつもりの再送」を静黙な二重記帳にしてしまい、409 だけが真相を利用者に見せられる。
- 競合の処理は二層。逐次再送は書き込みトランザクション内の事前 SELECT で捕まえる。同時再送の敗者は
  一意制約違反で自トランザクションが作廃されるため、**トランザクション外**で catch し
  （`IntegrityViolations.violates` で制約名を検証、他の違反は素通し）、新しい読み取り専用トランザクション
  （`replayAdjust`）で再読して逐次と同一の比較ロジックへ落とす。この catch は **controller に置く** —
  `@StoreScoped` の切面は注入された EntityManager の現在セッションへ storeFilter を掛けるが、本リポジトリは
  OSIV を無効にしているため、サービス内で `TransactionTemplate` により後からトランザクションを開くと
  切面がフィルタを掛けたセッションと実クエリのセッションが食い違い、店舗分離が静かに外れる。書き込み腿を
  従来どおり `@StoreScoped @Transactional` のサービスメソッドに保ち、サービス代理の外側（controller）で
  catch するのが、フィルタ・トランザクション・catch 位置の三者を同時に満たす唯一の単純な形である。

## Consequences

手動調整の再送は何度届いても台帳に 1 行しか積まれず、応答は常に成功（現在残高）か 409（内容不一致）の
いずれかで、5xx にはならない。ダイアログを閉じて開き直した場合は新キー＝新操作であり、二回成立する —
これは判別不能であり防がない（防ごうとすれば内容一致で誤遮断するだけである）。

`CustomerPointService.adjust` は冒頭で顧客行を `findByIdForUpdate` で押さえるため、同一顧客への同時再送は
実際には行ロックで直列化され、ほぼ事前 SELECT の経路へ落ちる。一意制約とトランザクション外の catch は、
その直列化が効かない場合（将来の経路追加・ロック除去・顧客跨ぎのキー衝突）への最後の一枚である —
到達可能性の推論に依存せず、対象データの構造上の無条件不変量として置く。

取消・失効・退会消去の各経路を実装する票は、書き込みが「利用者の再操作で二度届きうるか」を判定し、
届きうるなら本機構（キー列＋一意制約＋トランザクション外再読）を再利用すること。受注完了のように
前提状態の遷移が再送を遮断する経路では不要である。
