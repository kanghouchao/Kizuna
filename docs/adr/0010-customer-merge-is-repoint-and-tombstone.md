# 顧客統合は付替えと墓標で表し、行を削除しない

Status: Accepted

## Context

旧システムには「重複顧客を一つにまとめ、受注・連絡先・履歴・ポイント・特典を統合先へ関連付け直す」
顧客統合が実在し、移行後も同等の能力が要る。統合を後から足すと帰属のやり直しになるため、形状を先に
決める。公開仕様上の型は三つ: 破壊的統合（Square / Shopify — 新レコード生成＋旧削除、履歴の断絶を仕様
として受容）、双方向リンク（FHIR `Patient.link` — 行を残しリンクで同一性を表す）、派生ビュー
（Dynamics 365 CI — ソース行を残し統合プロファイルを生成）。

本系で Customer を参照するのは受注と関連の 2 本の外部キーだけである。ポイントは会員に帰属し
（ADR 0006）、受注帰属記録は受注と会員を参照する（ADR 0009）— どちらも Customer 行を参照しない。
旧システムで統合の最重量部だったポイント・特典の付替えは、本系の形状では**そもそも発生しない**。

## Decision

- **付替え＋墓標＋統合履歴**。存続行へ被統合行の受注（全状態）と関連（ACTIVE・RELEASED の区間史ごと）を
  付け替える。被統合行は削除せず、統合先参照を持つ墓標として残し、電話照合・一覧の既定表示・新規の
  関連成立先・受注の顧客指定から除外する。旧 ID の解決は統合先へ届く。
- **連鎖は圧平する**: B を C へ統合するとき、B を指す既存の墓標もすべて C へ付け替える。解決は常に
  一跳であり、読み手にリンク追跡の税を課さない（双方向リンク型を採らない理由）。
- **両行が ACTIVE 関連を持つ統合は拒否する**。部分一意により両者は必ず別会員を指す — 二人の本人が
  それぞれ認領している行を機械や統合画面の片手間の判断で片付けさせない。先に理由の残る解除を経てから
  統合する。「これは同一人物か」（台帳級の判断）と「どちらの会員の認領が正しいか」（本人の今後の
  ポイント帰属に関わる証明級の判断）を一画面に混ぜない。
- **フィールド値の自動合併はしない**。存続行は自分の値を保ち、必要な転記は統合時に人が見て行う。
  空欄の自動補完も採らない — 静黙なデータ混合は、どの値が本人申告でどれが機械転記かを消す。
- **統合の取消（undo）は無い**。統合後の存続行には新しい受注・関連が積まれ、機械的な巻き戻しには
  解が無い。統合履歴（実行者・日時・移したもの）を機微情報として残し、誤統合の修復は履歴を根拠と
  する人手作業とする。訂正を機械の級聯にしない紀律は ADR 0009 と同じ。
- **重複候補の提示は手がかり、実行は常に人手**。同店電話一致を第一の検出器とする（複数一致で自動照合を
  断念した行群は天然の候補入口）。機械による自動統合は行わない。
- 統合は同一店舗内に閉じる。店舗を跨ぐ同一人物は会員関連で表す（Customer は単一店舗帰属）。

## Consequences

- ポイント台帳・受注帰属記録・会員の来店履歴は統合の前後で不変 — 会員側からは統合は見えない。
- 読み手（照合・一覧・解決）は「生きている行」だけを見ればよく、被統合行の存在を知る必要があるのは
  旧 ID の解決と統合履歴の閲覧だけである。
- 誤統合の修復は稀で重い人手作業になる。これは自動 undo の誤爆リスクと引き換えに受け入れる。
- 外部キーの onDelete 連鎖（関連は CASCADE）に統合が触れることはない — 行を消さないため。
