# 今回限りの業務連絡許可 — HTTP 契約

状態: 承認済み（2026-09-25）。関連: #961、#955、ADR 0028。

## 許可の単位と不変条件

受注の受付時の写しにある電話・メール・LINE のそれぞれについて、今回限りの業務連絡可否を記録する。顧客・顧客連絡先の登録は不要。入力だけでは許可せず、未記録は `UNKNOWN` とする。販促への流用、顧客台帳への書き戻し、連絡先一致による顧客関連は行わない。

許可は種類と正規化値に結び付く。電話は日本番号を +81 に統一し、メールは前後空白除去とドメイン部小文字化、LINE は前後空白除去とする。宛先の変更・削除では元の許可を失効させ、同じ保存操作で新しい根拠を明示しない限り `UNKNOWN` に戻す。同値の表記調整では維持する。過去の根拠と変更前後は履歴に残す。

## HTTP

以下は既存の API ベース配下のパス。すべて `ORDER_MANAGE` とアクセス可能な店舗コンテキスト（`X-Role: store`、`X-Store-ID`）を要求する。顧客台帳の変更は行わず、`CUSTOMER_MANAGE` は要求しない。

| メソッド・端点 | 契約の変更 | 成功 |
| --- | --- | --- |
| `POST /store/orders` | 作成要求に `business_contact_permissions` を追加 | 201、既存の受注詳細 |
| `PUT /store/orders/{id}` | 編集要求に同項目を追加。既存の `expected_version` は必須 | 200、既存の受注詳細 |
| `POST /store/orders/preview` | 作成と同じ追加項目を検証。保存・履歴追加はしない | 200、既存の試算応答 |
| `POST /store/orders/{id}/preview` | 編集と同じ追加項目を検証。保存・履歴追加はしない | 200、既存の試算応答 |
| `GET /store/orders/{id}` | 詳細に現在の許可と最新の判定を追加 | 200 |
| `GET /store/orders/{id}/business-contact-permission-history` | 操作履歴を取得 | 200、`CursorPage` |

既存要求の他の項目・必須条件と受注の編集可能状態は変更しない。申請確認時の同意取り込み、ゲスト・会員の要求／応答、公開画面は後続票のため変更しない。店舗で受注を作成した後は既存の編集経路から許可を記録できる。

### 書き込み

`business_contact_permissions` は省略可能な配列で最大 3 件。同種類は 1 件まで。省略・null・空配列はいずれも明示的な許可変更なしとする。ただし宛先変更による失効は常に適用する。配列内の null 要素は拒否する。

各要素の全項目は必須かつ null 不可。

| 項目 | 型・制約 |
| --- | --- |
| `type` | `PHONE / EMAIL / LINE` |
| `status` | `UNKNOWN / ALLOWED / DENIED` |
| `source` | 空白以外を含む文字列、最大 200 文字 |
| `reason` | 空白以外を含む文字列、最大 2000 文字 |

対象の値は保存後の `contact_snapshot` から解決し、対象宛先がない指定は 400。任意の別宛先に許可を登録する要求は受けない。状態を `UNKNOWN` に明示変更するときも出所・根拠を要求する。実行者・時刻はサーバーが記録する。受注、許可、履歴は同一トランザクションで保存する。

### 詳細応答

受注詳細の `business_contact_permissions` は常に配列で返す。写しの宛先ごとに最大 3 件、順序は PHONE、EMAIL、LINE。宛先がなければ空配列。

各要素は `type`（上記 enum）、`value`（正規化済み文字列）、`status`（上記 enum）、`source`・`reason`（文字列または null）、`recorded_by`（操作者 ID、整数または null）、`recorded_at`（オフセット付き ISO 8601 日時または null）、`decision`（下記 enum）を持つ。未記録では状態 UNKNOWN、記録項目は null。操作者削除後も根拠と日時を保持する。

`decision` は `ALLOWED / STORE_DENIED / NOT_ALLOWED`。同店の有効な業務拒否があれば `STORE_DENIED`、拒否なしで今回の状態が ALLOWED なら `ALLOWED`、それ以外は `NOT_ALLOWED`。顧客 ID・拒否者の氏名・内部資料は返さない。この判定は表示時点の参考であり、送信許可トークンではない。作成・編集の詳細応答にも同じ形を返す。一覧 DTO には追加しない。

### 操作履歴

クエリは `cursor?: string`、`size?: integer`（既定 20、1〜2000 に制限）。`content` 配列と、続きがある場合の `next_cursor` 文字列を返す。履歴 ID の降順を全順序としてカーソルにも同じキーを用いる。

各履歴は `id: string`、`type`、`action: RECORDED / CONTACT_CHANGED`、`before`、`after`、`recorded_by: integer | null`、`recorded_at: string` を持つ。`before` / `after` は `{value: string, status, source: string | null, reason: string | null}` または null（宛先追加前／削除後）。明示操作は新しい根拠を保持し、宛先変更による失効は action と前後の宛先・状態で識別する。履歴の更新・削除 API は設けない。

### 主な失敗

- 400: 型・長さ・重複種類・宛先なし・不正なカーソル、既存規則で編集できない状態。
- 401: 未認証。403: 操作権限または店舗アクセスなし。
- 404: 受注が存在しない、または店舗スコープ外。
- 409: 受注の版競合など、既存の競合条件。

エラーは既存の `{error: string, details?: object}`。店舗拒否があること自体は記録の失敗にしない。今回の同意の証拠は保存し、実効判定だけを不許可にする。

## 送信側への公開境界

ここでの公開境界は匿名 HTTP API ではなく、Spring Modulith の名前付きインターフェースとする。受注 ID・連絡先種類から保存済みの宛先と今回の許可を読む受注側の入口と、店舗・種類・正規化値に対する業務拒否の有無を返す顧客側の入口を分離する。

確認前申請でも同じ拒否判定を呼べるように、顧客側の入口は顧客 ID・受注 ID・確認状態を要求しない。申請側の呼び出し元は保存済み申請の宛先と根拠付き許可を解決し、今回の状態と拒否結果を同じ規則で判定する。本票ではこの公開境界をテストし、ゲスト同意の取得・保存・確認時取り込みは追加しない。根拠のない申請は許可しない。

全未統合顧客の同種類・同値の有効連絡先を対象にする。選択中の顧客に限定せず、他店舗・削除済み連絡先・統合墓標は遮断理由にしない。既存の正規化規則を共有する。顧客台帳側の UNKNOWN は今回の明示許可を妨げず、DENIED が一件でもあれば停止する。

#394 は送信・再送の直前に毎回最新の保存状態で再判定し、以前の画面表示や判定結果を再利用しない。拒否の追加・根拠付き解除後は次の判定に反映する。判定例外時は送信しない。判定後の送信との競合制御は送信基盤の実装時に扱い、本票の判定結果を永続的な配信権としない。

公開名は `customer::contact` の `BusinessContactRestrictions.isDenied(type, value)`、`order::contact` の `BusinessContactPolicy.evaluate(type, value, status)` と `OrderBusinessContact.decide(orderId, type)`。店舗は授権済みの `StoreContext` から解決し、文脈なしでは失敗する。受注判定は判定対象の正規化済み宛先も返し、送信側はその宛先を用いる。

## 検証

HTTP 統合テストと実 PostgreSQL で根拠・履歴の再取得、宛先変更時の失効、保存の原子性、版競合、権限・店舗隔離を検証する。公開境界では別顧客選択・顧客未設定・確認前申請、拒否追加／解除後の再判定、他店舗・削除・統合墓標の除外を検証する。

店舗ページテストと日本語 E2E で明示選択、根拠必須、保存結果、拒否の表示と失敗後の回復を検証する。変更画面を実ブラウザで狭幅・長い値・両テーマ・キーボード操作について確認する。最終検証は Taskfile の lint・test・build・e2e。最後に code-review の Standards / Spec レビューを行い、実装をコミットする。
