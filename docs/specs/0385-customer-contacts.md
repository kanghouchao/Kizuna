# 顧客台帳の連絡先と連絡可否

状態: 確定（2026-09-20、全体確認済み）。新しい設計は未実装。
対象: [#385](https://github.com/kanghouchao/Kizuna/issues/385)。

## 確定した境界

- 連絡先は店舗の Customer に属し、他店舗や Member のログイン情報へ同期しない。
- 顧客と連絡先を別テーブルとし、一顧客が複数の連絡先を持つ。
- 未稼働のため、既存データの移行・旧構造の互換対応は対象外とする。
- 連絡可否も本仕様で定義する。#394 の送信基盤が参照する正本を担う。

## 連絡先と優先指定

- 電話・メール・LINE はそれぞれ複数登録でき、種類ごとに優先連絡先を最大一件指定できる。
- 優先指定は既定の表示・連絡先選択のためであり、本人性や連絡可否の根拠にはしない。
- 統合時に優先指定を解決する。両側の指定が衝突する場合は、最終的な一件または指定なしを明示する。
- 削除済みの連絡先は連絡・検索・重複候補の対象にしない。履歴は権限を持つ利用者が参照できる。
- 電話番号は日本の番号だけを受け付ける。入力時に検証・形式統一を行い、表記揺れによる同値判定の誤りを防ぐ。海外番号の受付は対象外。

## 検索と重複候補

- 検索と重複候補は、同一店舗の未統合顧客の全有効連絡先を対象とする。優先連絡先に限定せず、電話・メール・LINE の同種類・同値を手がかりとする。
- 候補には一致した種類と値を示す。人が確認して統合・関連付けを決め、自動で顧客や会員へ関連付けない。
- 電話は日本番号として検証して +81 の国際形式へ統一する。全入力経路で同じ規則を使い、表示形式の違いで別の番号にしない。
- メールは前後空白を除き、ドメイン部だけを小文字化する。ローカル部の大文字小文字・点・プラス記号の後続を勝手に同一視しない。LINE ID は前後空白を除いた値で比較する。
- 検索・候補検出・連絡可否の共同制約は同じ同値判定を使う。

## 受注と連絡先の独立性

- 受注の顧客参照は任意。顧客は連絡先なしでも存在でき、受注にも連絡先の登録を強制しない。
- 受注は今回の受付時の連絡先を独立して保存できる。顧客を選択した場合も同じであり、顧客連絡先の ID を必須にしない。
- 顧客連絡先の変更・削除・統合によって受注の受付時の写しを変更しない。臨時の連絡先を顧客台帳へ保存することも強制しない。
- 店舗での受注入力は連絡先から候補を探せるが、電話番号の一致による顧客の自動選択・自動作成は行わない。担当者が既存顧客・新規顧客・顧客未設定を選ぶ。
- 会員本人の申請は従来どおり認証済みの本人と会員関連から顧客を解決・作成する。連絡先による照合ではない。
- 設計理由と既存 ADR の変更範囲は [ADR 0028](../adr/0028-customer-contacts-and-order-contact-snapshots.md) を参照する。

## 統合と履歴

- 顧客統合では連絡先を全件付け替え、連絡先の ID と由来を保持する。同値の連絡先も黙って重複排除しない。
- 統合前に重複を提示し、整理は人の明示操作で行う。
- 連絡先の追加・変更・削除、連絡可否の変更は前後値・実行者・日時を残す。
- 統合履歴には双方の顧客、統合前後の会員関連、移動した受注・連絡先・会員関連の ID、資料の選択結果、実行者・日時・理由を記録する。自動取消は提供しない。
- 統合プレビューに双方の顧客資料を示す。存続側の値を初期値とし、人が選択・編集して確定する。注意事項は確認を必須とし、双方の原内容と確定内容を統合履歴に残す。

## 会員関連とポイント

- 一方だけが ACTIVE な会員関連を持つ場合、統合の向きに依らず存続顧客がその関連を保持する。
- ポイントは Member の台帳に属する。統合は残高を加算・移動せず、統合を理由とするポイント仕訳を作らない。
- 完了済み受注の既存帰属は不変。未帰属の過去受注も自動で帰属・付与せず、既存の伝票トークンによる事後申領を使う。
- 未完了受注は完了時の有効な会員関連で帰属を判断する。統合時点で帰属やポイントを確定しない。
- 統合プレビューに最終的な関連会員・現在残高・影響する未完了受注件数を表示し、残高の変更や過去分の自動付与がないこと、未完了分の完了時帰属への影響を明示する。
- 双方に ACTIVE な関連がある場合は既存の拒否を維持し、先に理由付きの関連解除を要する。

## 連絡可否

- 具体的な連絡先と用途の組で管理する。用途は業務連絡・販促連絡の二つ。
- 状態は未確認・許可・拒否。初期状態は未確認で、能動的な連絡は不可。
- 個別連絡と自動送信の双方で適用する。実際の送信は #394 の責務とする。
- 同一顧客の同種類・同値の有効な連絡先は用途別に共同で制約する。拒否を最優先、次いで未確認とし、全件許可の場合だけ許可する。別の有効な重複行を選んで制約を回避できない。
- 同値の有効行を残して一部を削除する場合、削除直前の共同制約を用途別に残存行へ引き継ぎ、削除と同時に履歴へ記録する。拒否行だけを削除して許可行を使える状態にせず、制約を緩めるには新しい根拠付きの明示的な許可変更を要する。種類・値の変更で旧値の集合から行が抜ける場合も同じ規則とする。
- 削除後に同値の連絡先を追加した場合は新規登録として両用途を未確認で開始し、削除済み行の拒否は引き継がない。削除前の状態は履歴に残す。有効な同値の別行が残る場合は、その行との共同制約が働く。
- 連絡先の実際の値が変われば両用途を未確認へ戻し、履歴を残す。表示形式や優先指定だけの変更は許可を失効させない。
- CUSTOMER_MANAGE を持つ利用者は出所と根拠を記録して連絡可否を代行登録できる。
- ゲスト申請では業務連絡の許可を必須とする。販促の許可は独立した任意項目とし、既定で選択しない。連絡先入力や会員関連の成立だけでは許可を与えない。
- 申請には連絡先と許可の原文を保存する。確認時に顧客の選択・新規作成と連絡先の取り込みを明示する。既存の拒否は新しい申請で黙って上書きしない。顧客未設定の場合も申請記録と受注の受付時の写しを保持し、顧客や顧客連絡先の行は作らない。
- 連絡先・連絡可否とその変更履歴は CUSTOMER_MANAGE、統合と統合履歴は CUSTOMER_MERGE で扱う。
- 本仕様の画面範囲は店舗担当者の管理とゲスト申請の許可取得。会員本人による連絡先・連絡可否の管理画面は対象外。

## 今回の申請・受注だけの連絡許可

- 顧客台帳へ登録しない連絡先でも、申請・受注は今回の業務連絡だけを許可する状態と根拠を独立して保持できる。顧客連絡先の行を必須にしない。
- ゲスト申請で取得した業務連絡の許可は、その申請と確認後の受注に利用できる。店舗の直接入力では担当者が今回の業務連絡の可否と根拠を記録し、連絡先の入力だけで許可しない。
- 今回だけの許可は販促に使わず、顧客台帳の連絡可否を自動変更しない。
- 今回だけの許可を使う連絡は、送信・再送の直前に同一店舗の全未統合顧客の同種類・同値の有効連絡先を照会し、業務連絡の拒否が一件でもあれば止める。確認前のゲスト申請、顧客未設定の受注、顧客選択済みの受注のいずれにも適用し、選択した顧客だけに検索を限定しない。
- 拒否がある場合は、新しい根拠に基づいて担当者が該当する顧客側の許可を明示的に変更するまで連絡しない。照会は連絡の制限だけに使い、申請・受注に顧客を自動設定せず、台帳への登録も強制しない。他店舗と削除済み行は照会対象外とし、拒否がなければ今回の許可で判断する。
- 申請時の原文と許可の根拠は保持する。原文を変えることと、その後の連絡可否の変更を混同しない。

## 顧客一覧と詳細

- 最終来店日は、その顧客の完了済みかつ無効化されていない受注の最新営業日とする。
- ポイントは現在の関連会員のプラットフォーム全体の残高を参照する。未関連は零と区別して表示する。
- 最終来店日・ポイントは昇順と降順を選べ、来店なし・会員未関連はそれぞれ両方向とも末尾に置く。
- landmark を顧客詳細と編集フォームに含める。

## 受け入れ条件

- 一顧客に同種類を含む複数の連絡先を保持でき、種類ごとの優先指定は最大一件。追加・変更・削除と連絡可否の前後値・実行者・日時を参照できる。
- 日本の同一電話番号は入力表記によらず同値となり、海外番号は受け付けない。非優先の電話・メール・LINE の一致でも重複候補を示す。
- 顧客を選択しなくても受注が成立し、電話入力だけでは顧客を作成・選択しない。顧客を選択した受注も今回の連絡先を独立保存し、台帳変更で書き換わらない。
- 会員本人の申請では認証済み本人による顧客整備が継続し、電話一致に依存しない。
- 統合は連絡先・受注・会員関連を付け替え、連絡先の ID と由来を保つ。優先指定と資料選択を確定し、双方の原資料と結果、移動した対象 ID、理由・実行者・日時を辿れる。
- 一方だけに会員関連がある統合は向きによらず関連を保ち、既存残高・確定済み帰属を変えない。未完了受注への影響を事前に示す。双方が ACTIVE なら統合を拒否する。
- 用途別の未確認・拒否では能動的に連絡できない。有効な同値の行が複数ある場合は拒否、未確認、許可の順で制約する。
- 値の変更では許可が未確認へ戻る。削除・再登録でも初期値へ戻り、削除済みの拒否は継承しない。各変更履歴は残る。
- 統合後に同値の拒否行と許可行があるとき、拒否行の削除または別の値への変更でも旧値の残存行は拒否を引き継ぎ、変更前後と由来を辿れる。未確認行と許可行の整理でも未確認を引き継ぐ。全行削除後の新規登録は未確認であり、過去の拒否を復活させない。
- ゲスト申請は業務連絡の許可を必須とし、販促を既定で許可しない。顧客未設定でも申請の証拠と受注の写しを保ち、今回だけの許可で顧客側の有効な拒否を迂回しない。
- PENDING のゲスト申請に今回の許可があっても、同店の同種類・同値の有効な拒否があれば確認前の連絡を止める。別顧客を選択しても回避できず、送信予約後の拒否も実送信・再送時に再検査する。他店舗だけの拒否や削除済み行は遮断理由にしない。
- CUSTOMER_MANAGE と CUSTOMER_MERGE の閲覧・操作境界を守り、他店舗の連絡先や履歴は参照できない。会員・公開向け応答に顧客の内部評価・注意事項・統合監査情報を含めない。
- 最終来店日と会員の全体残高を昇降順に並べられ、値なしは末尾となる。landmark を詳細表示・編集できる。

## 実装への引き継ぎ

- #331 / #333 の関連要件に本仕様を適用する。送信正本・配信手段・再送は #394 が担い、顧客側と今回限りの許可を送信時に参照する。
- 既存の会員関連の成立・解除の区間履歴、同店一会員一 ACTIVE 関連、顧客統合の墓標と一跳解決を維持する。
- 統合のプレビュー後に対象が変わった場合は古い選択で実行せず再確認させる。付替え・許可初期化・履歴を各操作と一体で確定する。
- 重複整理の履歴には除去元と制約を引き継いだ連絡先 ID、用途別の前後状態を記録する。制約継承は削除・値変更と一体で確定し、本人の新しい同意として記録しない。
- API の具体的なパス・型・エラー・ページングは実装前に backend/AGENTS.md の契約規約に従って提示する。本票の業務判断の確定は HTTP 契約の承認を兼ねない。
- 既存データの移行、旧 API との互換、送信基盤の実装、会員セルフサービス画面は本票の対象外。
