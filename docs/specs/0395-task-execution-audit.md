# 定期処理と業務監査の共通基盤

## 背景と今回の範囲

サービス ID の管理と緊急昇格は実装済みだが、処理の実行・失敗・再実行を追跡する共通基盤はない。本票は既存の身分を利用し、実行記録と変更不可の業務監査を追加する。実際の入出金、精算確定、給与締めを新設しない。

実装は次の順序とする。各段階の完了だけで親 issue 全体を完了とはしない。

1. サービス ID による処理実行、失敗の保持、再試行、実行履歴の照会。後続のポイント失効処理が利用する公開境界を提供する。
2. 変更不可の共通監査と管理画面。既存の業務事実を保持したまま、サービス ID・緊急昇格・権限変更・受注訂正・顧客統合・手動ポイント調整の成功操作を接続する。
3. 各域の監査網羅性と通知要求の接続を検証する。外部への通知送信は通知基盤の責務であり、本変更では有効化しない。

## 決定

- 実行対象はコードに登録された処理だけとする。SQL、クラス名、任意コードを利用者入力から実行しない。
- 実行主体は現在有効な SERVICE に限定する。処理が宣言した権限と対象店舗を開始時に DB で確認する。平台全体の処理は ALL_STORES を要求する。JWT を発行・偽造せず、人のセッションを借用しない。
- 同一処理名と論理実行キーは一つの要求を指す。同じ入力の再送はサービス ID の停止・撤権後も最新の試行を返し、異なる入力でのキー再利用は競合とする。HTTP 呼出者の現在の管理権限と対象範囲は毎回検証し、新規実行・別試行の作成にはサービス ID の現在の権限を要求する。業務側の冪等性・残高ロックをこの鍵で置き換えない。
- 開始記録を先にコミットする。業務更新と成功記録は同一トランザクション、失敗記録は業務ロールバック後の独立トランザクションで保存する。処理は同じ DB 内の有界な仕事とし、外部送信はその専用基盤に委譲する。
- 再実行は失敗した最新試行から別の試行を作り、原記録と理由を保持する。開始時にサービス ID の権限を再検証する。成功済み要求や実行中要求の再実行は拒む。
- プロセス停止などで結果が不明の実行中記録は自動再実行しない。行ロック取得と開始からの猶予を確認した明示的な中断記録によってのみ再試行可能にする。時間超過だけで稼働中処理を奪わない。
- 実行履歴の主体・店舗 ID と表示名は記録時の値を保持し、利用者や店舗の削除に連動させない。期間の帰属は注入した業務時計で確定する。
- 成功した業務操作の監査は同じトランザクションで追記する。監査の保存失敗時は業務もロールバックする。共通監査表の UPDATE / DELETE / TRUNCATE は DB で拒否する。
- 受注訂正、顧客統合、ポイント仕訳、緊急昇格の既存表は業務事実の正本として残す。共通監査にはそれらの ID と必要な変更摘要を保存し、個人連絡先・秘密・例外原文を複製しない。
- 監査と実行管理には専用権限を追加し、既定ロールへ自動授与しない。全店舗にまたがる履歴の参照・操作は現在 ALL_STORES の STAFF に限定する。実在アカウントの権限は変更しない。
- 保持年限が未確定のため自動削除を設けない。過去に存在しなかった監査を遡及生成しない。
- 運用環境の定期処理は本作業で有効化しない。まず無副作用のサービス ID 検証処理で実行から照会までを確認する。

## HTTP 契約

JSON は snake_case。認証失敗 401、権限不足・ALL_STORES 不足 403、不可視または不存在 404、入力不正 400、実行状態・論理キーの競合 409。エラーは既存の error/details 形式を用いる。

| 端点 | 成功 | 要求と応答 |
| --- | --- | --- |
| GET /platform/task-executions | 200 | cursor 任意、size 既定 50・上限 2000。開始日時と ID の降順 CursorPage。試行 ID、要求 ID、処理名、対象、期間、サービス主体、実行元、状態、開始・終了時刻、件数・固定失敗コードを返す |
| GET /platform/task-executions/service-identities | 200 | page 既定0、size 既定20・上限100。TASK_EXECUTE と ALL_STORES を持つ有効な SERVICE の ID・表示名を Page で返す。表示名・ID 昇順 |
| GET /platform/task-executions/{id} | 200 | execution に一覧情報、logical_key / retry_of / reason / initiated_by に詳細を返す |
| POST /platform/task-executions | 201 / 200 | task_name、logical_key、service_user_id、store_id 任意、period_start、period_end。新規試行は 201、同一要求の再送は 200。終了した試行を返す |
| POST /platform/task-executions/{id}/retries | 201 | reason 必須。最新の失敗・中断試行だけを対象とし、別の試行を返す |
| POST /platform/task-executions/{id}/interruption | 200 | reason 必須。実行中の古い試行を行ロック取得後に中断として記録する |
| GET /platform/audit-events | 200 | cursor / size、action 任意。発生日時と ID の降順 CursorPage。主体・対象・操作・結果・日時・参照元を返す |
| GET /platform/audit-events/{id} | 200 | event に一覧情報、before_values / after_values に明示的に選別した変更前後の文字列 Map を返す |

task-executions は TASK_MANAGE、audit-events は AUDIT_VIEW を要求する。サービス ID 検証処理の主体は TASK_EXECUTE を保持する。新規権限の既定授与はない。

## テスト境界

公開実行サービスと公開 HTTP 境界を主な seam とする。停止主体・範囲違反・権限不足、同一キー再送、入力衝突、再試行時の再授権、成功と業務更新の原子性、失敗保持、実行中の競合を検証する。PostgreSQL による制約・行ロック・監査変更拒否は実 DB でも検証する。UI はエラー・空・詳細・再試行とキーボード操作を確認する。

最終検証は Taskfile の lint / test / build / e2e と code-review。終了コードのみで合否を記録する。

## 後続処理の接続

`TaskHandler` を Spring bean として登録する。`name()` は処理識別子、`permission()` は SERVICE が保持すべき権限、`platformWide()` は店舗指定の要否、`execute(TaskContext)` は同一取引内の DB 処理と非負の処理件数を返す。`TaskContext` は executionId / serviceUserId / storeId / periodStart / periodEnd を含む。

`TaskExecutor.executeScheduled(new TaskCommand(taskName, logicalKey, serviceUserId, storeId, periodStart, periodEnd))` は JWT・店舗コンテキスト・既存取引の外から呼ぶ。`Submission` の created と execution を返す。状態は RUNNING / SUCCEEDED / FAILED / INTERRUPTED。実行要求ごとに一意な論理キーを生成し、業務日付は呼出側で業務時計から一度確定する。登録数は32を上限とする。

緊急昇格の通知要求は `EMERGENCY_NOTIFICATION_REQUESTED` 監査イベント（delivery_state=PENDING）として保存する。外部配信、配信先・再送管理は #394 の通知基盤が担当する。現時点で配信済みを意味しない。

監査表の拒否トリガーは通常の SQL 更新を止める。DDL を変更できる DB 所有者・管理者に対する耐改ざん保管ではない。保持年限は未確定で、更新・削除 API と自動削除は設けない。

## PostgreSQL の追加検証

`TaskPostgresTest` は専用の使い捨て DB のみを対象とする。`KIZUNA_TASK_TEST_JDBC_URL` に接続先を与え、`./gradlew test --tests '*TaskPostgresTest' --rerun-tasks` で実行する。通常の unit test は外部 DB を要求しないため、この6件だけ接続先未指定時にスキップする。既存開発 DB を指定しない。2つの JPA コンテキスト間の重複抑止、失敗と成功の原子性、稼働中のロック、中断復旧、権限再検証、監査変更拒否を検証する。

## このバッチだけでは完了しない受け入れ項目

#395 は本 PR で閉じない。緊急昇格中の操作は、今回接続した重要操作では利用記録へ関連付くが、通常受注編集など未接続の書き込み全般の変更前後までは収集しない。この緊急利用の網羅性は #395 の残件であり、通知送信 #394 とは別である。月次ロック解除 #389 と未実装の各業務処理は、機能の実装時に同じ監査境界へ接続する。外部送信・保持年限・実際の定期処理有効化も本バッチの完了に含めない。

### 緊急昇格監査の後続切片

現行の昇格トークンは全 STORE 権限を与えるため、既存の重要操作への接続だけでは網羅できない。2026-10-07 の store controller 棚卸しに基づき、以下を個別に実装・検証する。読み取りと変更しない preview は対象外。

| 切片 | 未接続の変更操作 | 主な実装境界 |
| --- | --- | --- |
| 受注の通常操作 | 登録・編集・完了・取消、申込の確定／拒否、特殊サービス開始 | OrderService、OrderApplication の確定／拒否、特殊サービス処理 |
| 会員帰属・ポイント関連 | 受注帰属の無効化／訂正、伝票トークン再発行、ポイント巻戻し、顧客と会員の関連付け／解除 | 既存の帰属・訂正・巻戻し・関連区間の業務記録 ID を共通監査へ接続。トークン生値を含めない |
| キャスト・勤務 | キャスト登録／編集／削除・公開・停止／再開／退店・招待、カスタム項目の登録／編集／削除、シフト CRUD／公開、出勤申請承認／拒否、出勤実績登録／訂正／取消 | cast / shift の既存アプリケーションサービス。招待秘密・個人情報・自由記述を複写しない |
| 顧客・連絡 | 顧客 CRUD、連絡先 CRUD、用途別許諾、優先連絡先 | customer の各アプリケーションサービス。連絡先値を複写せず、既存履歴と変更項目・許諾状態を参照できる形にする |
| 店舗設定・提供内容 | 店舗プロフィール更新、サービス設定 CRUD、ファイル登録 | storeprofile / service / storage の境界。外部ストレージとの確定順序は別途検証し、ファイル内容や認証情報は記録しない |
| 共通の網羅性検証 | 上記の成功操作への昇格 ID 関連付け、失敗／競合／再送時の監査の一貫性 | 通常主体と昇格主体の比較、業務＋監査の同一取引、権限不足・異店舗拒否、秘密非混入を HTTP と DB で検証 |

本バッチで接続済みの受注訂正／完了無効化、顧客統合、手動ポイント調整、スタッフ授権は再実装せず、同じ一覧で接続状態を管理する。追加される採用管理 #396 等の STORE 機能も昇格対象に入るため、機能追加時に共通監査へ接続する。
