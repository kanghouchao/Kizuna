## #820 実装仕様（#381 / #807 の確定裁定に基づく）

### 問題と解決
期限切れロットを残高から除外する現行規則を維持し、未消費量を会員ごとに一つの EXPIRE 仕訳へ記帳する。参照は書き込まない。通常付与の無期限も変更しない。

### 利用者の要件
1. 運用者は日次処理の対象日、実行元、結果、処理件数を共通実行履歴から確認できる。
2. 会員の期限内残高は失効記帳の前後で変わらず、期限当日と無期限ロットは失効しない。
3. 運用者は充当行から元ロットの期限、仕訳から処理日時、共通監査から実行試行を辿れる。
4. 再送・競合・失敗後の再試行は二重引当を生まず、利用取消で期限切れロットへ戻った量も後続実行で記帳できる。

### 実装判断
- #395 の TaskExecutor / TaskHandler / AuditWriter を利用する。SERVICE・ALL_STORES・TASK_EXECUTE・POINT_EXPIRE を物化前、各監査前、最後の検証点で別の短い READ_COMMITTED 取引から検証する。物化と監査は同じ外側の取引で、撤権検出時は全て取り消す。最後の検証後の撤権は次回の境界から有効になる。
- 手動の新規実行・再試行は STAFF に TASK_MANAGE・POINT_EXPIRE と ALL_STORES を要求する。履歴・候補取得は従来どおり TASK_MANAGE。既存要求と完全一致する再送は新しい処理を起こさず、後日の SERVICE 撤権で既存結果を失わない。
- 基準日は app.timezone の暦日。日付変更時刻は適用しない。過去日の補実行を許可し未来日は拒否する。対象日までに期限切れとなった未消費分を累積で拾う。
- 同一論理キーの再送と失敗再試行は共通実行基盤へ委譲する。台帳は実行試行・会員から作る一意キーを持ち、actor は持たない。
- 消費・取消と同じ元ロットの行ロックを取り、ロック取得後に USE_CANCEL を含む純消費を再集計する。
- 一試行は一取引。途中の会員または監査が失敗すれば仕訳全体を取り消し、共通基盤だけが失敗履歴を保存する。
- 読み込みロット数は設定上限+1で検出し、超過時は部分成功にせず失敗する。金額合計の int 超過も同様に拒否する。制限時間は共通基盤の設定に従う。
- 日次起動は既定で無効。最終アダプタは executeScheduled にのみ委譲し、独自実行器・暫定スケジューラ・本番有効化は作らない。

### 検証
既存のドメイン計算器、TaskExecutor 経由の PostgreSQL/E2E 境界で、期限・残高不変・再送・並行消費/取消/再実行・主体失効/範囲変更・途中失敗回復・上限を検証する。

### チケット
既存 #820 を一つの縦切りとして使用する。依存は #395。重複子票と #381 の変更は作らない。通知、期限政策変更、既存データ清掃、デプロイは対象外。

### API 契約

- `GET /platform/task-executions/service-identities?task_name=POINT_EXPIRY&page=0&size=20` は既存の Spring Page（`content: [{id: number, display_name: string}]` とページ情報）を返す。`task_name` 省略時は `SERVICE_IDENTITY_CHECK`、`page` は 0 以上、`size` は 1〜100。未知の処理名・不正ページは 400。
- 候補取得と履歴取得は現行の STAFF・有効状態・`TASK_MANAGE`・ALL_STORES を要求し、違反は 403。SERVICE 候補は有効・ALL_STORES・`TASK_EXECUTE`・処理固有権限を満たすものだけを DB でページングする。
- 既存 `POST /platform/task-executions` の `task_name` に `POINT_EXPIRY` を指定する。`logical_key: string`、`service_user_id: number`、`store_id: null`、`period_start: YYYY-MM-DD`、`period_end: YYYY-MM-DD` は従来形式。対象日は同一の一日とする。新要求は 201、完全一致の再送は 200、同じキーの異なる要求は 409。
- 新規実行と `POST /platform/task-executions/{id}/retries` は操作者の `POINT_EXPIRE` も要求する（不足は 403）。完全一致の結果再取得は新規処理ではないため追加の業務権限を要求せず、従来の管理権限は引き続き必要。SERVICE の二権限と範囲は新規実行・再試行の双方で検証する。
- handler 内で対象日・ロット数・授権・監査の検証が失敗した場合は、共通実行基盤が取引を取り消して FAILED を返す。未来日の新要求も履歴が作られるため 201 / FAILED となる。履歴・詳細・再試行の応答形式は変更しない。

### 検証境界

専用 PostgreSQL 18 の二つの JPA コンテキストを使い、元ロットの実ロック待機を確認してから消費・取消を確定する。物化後の撤権は EXPIRE INSERT 後のトリガー待機で再現し、別接続の撤権確定後に処理を再開して、既存の消費 30 が残り EXPIRE と監査だけが取り消されることを確認する。REPEATABLE_READ と既読のロール集合でも確定済みの撤権を再取得し、接続プール枯渇は部分記帳なしの FAILED になることを検証する。
